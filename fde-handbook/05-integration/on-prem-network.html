內網、防火牆與資料落地

客戶環境的現實限制，以及如何提早規劃

這個技能是什麼

許多客戶（金融、醫療、製造、政府）的系統在內網，對外連線受限，資料不能離開特定地區或機房。這些限制會直接決定你能用哪種模型、怎麼部署、要等多久審批。

為什麼 FDE 需要它

網路與環境的限制，是專案延誤最常見的非技術原因之一：防火牆開通要一到三週、公司 Proxy 會讓憑證驗證失敗、測試環境與正式環境不同。FDE 要在專案初期就問，並把等待時間排進計畫。

怎麼做

開工前必問的清單

問題為什麼重要
你的程式要跑在哪裡？（客戶機房、客戶的雲端、我方雲端）決定部署方式與資料流向
能不能連到外部網際網路？經過 Proxy 嗎？模型 API 在外部時，必須能出去
防火牆要開哪些網址與埠？誰負責？多久？把等待時間排進計畫
公司是否做 TLS 檢查（會替換憑證）？會造成憑證錯誤，要安裝客戶的根憑證
資料能不能離開客戶環境？離開到哪裡？決定是否能用外部模型服務
資料有地區限制嗎？影響服務供應商與區域選擇
開發、測試與正式環境的差異？避免「測試過但上線失敗」
誰能核准上線與變更？週期？變更窗口可能一個月才一次

常見的部署選項與取捨

選項特性取捨
呼叫外部的模型服務最簡單、模型最新資料出境；需要審查與連線開通
客戶雲端中的模型服務資料留在客戶的雲端租戶與區域可選模型與功能受限；要由客戶設定
完全本地部署的模型資料不離開機房硬體與維運成本；模型能力與更新受限；要做評測確認夠用
混合敏感部分在本地，非敏感部分用外部設計與稽核更複雜

各供應商的區域、資料保留與部署選項會變動，請以客戶採用的供應商最新的官方文件與合約為準。

.NET 的小提醒

  • 透過 Proxy 連外時，要在 HttpClient 的 handler 設定 Proxy 與認證；環境變數 HTTPS_PROXY 並非所有情況都生效，請實際測試。
  • TLS 檢查造成的憑證錯誤，正確作法是把客戶的根憑證安裝到信任存放區；不要為了方便把憑證驗證關掉。
  • 客戶環境的 .NET 版本與設定可能受限，請提早確認能否安裝 .NET 8，或要用 .NET Framework。

業界情境

示意情境：等了三週的防火牆

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：銀行客戶的專案，FDE 第二週才提出「需要連到模型服務」的網路申請，審批週期是三週。專案原本的展示日因此延後。

  • 預防：第一次會議就問網路與審批流程；同時用遮罩後的樣本與替身繼續進行，避免等待時完全停擺。
  • 同時準備：一份給客戶資安的連線說明（目的地、埠、資料內容、遮罩、稽核）。

常見錯誤

  • 等到要上線才問網路。
  • 為了趕時間把憑證驗證關掉。
  • 只在自己的筆電上測試，沒有在客戶環境驗證。
  • 假設客戶能快速開通。

非程式領域怎麼用

非程式領域版

非程式專案也有環境限制：客戶規定不得使用外部的 AI 工具、不得上傳含個資的文件。先確認「哪些工具核准可用」，再設計流程，否則做好的流程無法使用。

怎麼練

  • 替你的專案寫一份「環境與網路需求單」：要連什麼、為什麼、資料是什麼、誰負責。
  • 列出「若連不到模型服務」時，你如何繼續進行（替身、遮罩樣本）。

可觀察的證據
