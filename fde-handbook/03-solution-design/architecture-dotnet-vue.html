.NET MVC＋Vue 的架構

把模型接進 ASP.NET Core MVC＋Vue 專案時，各層放什麼

這個技能是什麼

在同一個 .NET 專案中，前端由 Vue 負責畫面與互動，MVC 的 API Controller 負責輸入與輸出，服務層負責業務規則與流程，外部依賴（模型、資料庫）則放在介面之後。

為什麼 FDE 需要它

AI 應用最常見的架構錯誤，是把模型呼叫直接寫在 Controller 或前端。這會讓你無法測試、無法替換模型、無法在呼叫前後加入遮罩、驗證、稽核與規則。把模型當作「不可信的外部依賴」，放在介面之後，是最重要的一個決定。

怎麼做

技術範例以 ASP.NET Core MVC（.NET 8）＋ Vue 3，前後端同一個 .NET 專案為基準，並以練習專案 sample/TicketDesk 為例。若你的專案是 .NET Framework 的 ASP.NET MVC 5，觀念相同，但建置與測試指令、專案檔格式不同。

分層圖

Vue（畫面、核可、編輯草稿） └─ fetch → /api/... MVC API Controller（輸入驗證、HTTP 結果；不放業務規則） └─ TriageService（流程：遮罩 → 呼叫 → 驗證 → 規則 → 稽核） ├─ PiiMasker / InjectionDetector（純函式，容易測） ├─ ILlmClient（介面）──┬─ FakeLlmClient（測試與練習） │ └─ AnthropicLlmClient（真實模型） └─ IAuditLog / ITicketStore（持久化的介面）

為什麼這樣分

  • ILlmClient 介面：測試用替身、可重現的評測、日後更換模型或供應商都不改業務程式。
  • 驗證與規則在服務層：「模型說的」永遠要經過「我們的規則」才成為結果。
  • 前端不直接呼叫模型：金鑰不能放在瀏覽器；呼叫也無法被稽核與限流。
  • 純函式獨立出來：遮罩、偵測這類邏輯用單元測試就能涵蓋。

程式範例：TicketDesk 的註冊方式

builder.Services.AddSingleton<IAuditLog, InMemoryAuditLog>();
builder.Services.AddScoped<TriageService>();

var apiKey = Environment.GetEnvironmentVariable("ANTHROPIC_API_KEY");
if (Environment.GetEnvironmentVariable("TICKETDESK_LLM") == "anthropic"
    && !string.IsNullOrWhiteSpace(apiKey))
{
    builder.Services.AddHttpClient<ILlmClient, AnthropicLlmClient>(
        (http, _) => new AnthropicLlmClient(http, apiKey, model));
}
else
{
    builder.Services.AddSingleton<ILlmClient, FakeLlmClient>();
}

預設使用替身；只有明確設定環境變數才連真實模型。金鑰只從環境變數讀取。

同步、串流與背景工作

情境作法備註
使用者等待一個短回應同步 API設逾時；顯示處理中
長回應想即時顯示串流（Server-Sent Events 等）見串流到 Vue
大量批次（處理幾千封信）背景工作＋佇列要有重試、進度與失敗清單；注意成本上限

.NET Framework（MVC 5）的差異

  • 依賴注入需自行配置容器；非同步與 HttpClient 的使用方式不同（注意 HttpClient 要重複使用）。
  • 設定與機密：用 Web.config 的環境替換或外部機密管理，不要提交金鑰。
  • 概念（介面、分層、驗證）完全相同。

業界情境

示意情境：把模型呼叫寫在 Controller 的後果

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：原型階段把呼叫直接寫在 Controller 裡。三週後客戶要求：(1) 個資不可送出、(2) 要有稽核紀錄、(3) 換成客戶指定的供應商。

  • 三個需求都需要改 Controller，而且沒有測試保護，每次修改都要手動測。
  • 如果一開始就有 ILlmClient 與服務層，三項各自是一個小改動，而且能被自動測試確認。

常見錯誤

  • 把提示、金鑰、驗證邏輯散落在多個檔案。
  • 前端直接帶金鑰呼叫模型。
  • 在 Controller 放業務規則，導致無法單元測試。
  • 沒有替身，每次測試都要花錢連模型。

非程式領域怎麼用

非程式領域版

非程式版的「分層」是：誰負責輸入（表單或信箱）、誰負責規則（檢核表與審核）、誰負責執行（人或系統）。把「AI 建議」放在規則之前，而不是直接成為結果。

怎麼練

  • 打開 sample/TicketDesk，在 TriageService 找出所有「不信任模型輸出」的地方，列成清單。
  • 寫一個新的 ILlmClient 實作，永遠回傳固定結果，用來測試「模型出錯時」的分流行為。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 能畫出你專案的分層圖，並指出模型被隔離在哪一層；測試可以在沒有網路的情況下跑完。
