固定流程或自主 agent

先用最簡單的，只在需要時增加自主性

這個技能是什麼

Anthropic 在〈Building effective agents〉中區分兩種系統：workflow（工作流）是由預先寫好的程式路徑來編排模型與工具；agent 則是由模型自己決定流程與工具使用。

為什麼 FDE 需要它

這個選擇決定了可預測性、成本、延遲與風險。文章的建議是：從最簡單的解法開始，只在需要時才增加複雜度；許多情況下，一次模型呼叫搭配檢索與範例就足夠。Agent 以延遲與成本換取更好的表現，也可能讓錯誤累積，需要大量沙盒測試與護欄。

怎麼做

選擇的順序

  1. 不用模型：規則確定時，用程式。
  2. 單次模型呼叫（加提示、範例、檢索）：分類、擷取、摘要、草稿多半在這一層。
  3. 固定流程（workflow）：多個步驟，但路徑可預先決定。
  4. 自主 agent：步驟數與路徑無法預先決定，且你能承受它的成本與風險。

常見的工作流模式

原文整理了數種模式（以原文為準，下表是本手冊的簡述）：

模式做法適用
串接（chaining）前一步的輸出給下一步，中間可加檢查任務可以清楚拆成固定的幾步
路由（routing）先分類，再交給不同的處理流程不同類型需要不同的處理（客服分流）
平行（parallelization）同時做多份獨立工作，或同一工作多次再比較要加速，或需要多個角度
協調者與工作者一個模型拆任務、分派、彙整子任務無法事先列出
評估者與優化者一個產出、一個評論，迭代改進有明確的評估標準，且迭代有價值

決策的問題

  • 步驟與順序能不能事先寫死？能 → workflow。
  • 出錯時能不能回復？不能 → 加人工核可，或不要讓它自主。
  • 延遲與成本能不能接受多輪呼叫？不能 → 簡化。
  • 你能不能為它建立評測與監控？不能 → 不要上自主 agent。

在 TicketDesk 中

它是「路由」模式：先分類，再依類別給草稿，最後由人核可。整個流程由 TriageService 的程式碼決定，模型只負責其中一個判斷，沒有讓模型自己決定下一步。

業界情境

示意情境：客戶想要「一個會自己處理客訴的 agent」

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：客戶聽過「自主 agent」，要求它自己查訂單、決定補償、寄信。

做法特性風險
全自主 agent模型自己決定查什麼、補償多少、是否寄出補償金額錯誤、被來信誘導（見提示注入）、難以稽核
路由＋草稿＋人核可（建議的第一版）模型分類並草擬，人確認補償與寄出低；效果有限但可量測

FDE 的角色是把「想要全自動」轉成分階段路徑：先用第二種取得數字與信任，再依證據擴大模型的決定範圍（見人機分工的信任階梯）。

常見錯誤

  • 因為「agent」很熱門就直接上，沒有檢查 workflow 是否足夠。
  • 讓模型決定高風險的動作（付款、刪除、寄出），卻沒有人核可。
  • 多輪自主呼叫，卻沒有成本與輪數上限。

非程式領域怎麼用

非程式領域版

非程式的同構：先用固定的作業流程與檢核表（workflow），只有在無法事先寫死步驟時，才讓 AI 自行規劃。例如月結對帳：固定步驟＋AI 找差異，通常比讓 AI「自己完成月結」更穩。

怎麼練

  • 替你正在做的題目，寫出「不用模型」「單次呼叫」「workflow」「agent」四種做法，並說明為何選擇其中一種。
  • 把一個 agent 方案改成 workflow，列出你失去與得到的東西。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 有一份設計說明，清楚寫出選擇 workflow 或 agent 的理由，以及自主性被限制在哪裡。

觸類旁通

觸類旁通

「用最簡單的可行解」是工程的通則：能用索引就不用快取、能用快取就不用分散式系統。AI 設計只是把這個原則應用到「模型有多少自主權」這個軸上。
