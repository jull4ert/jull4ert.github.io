自建、購買或設定

什麼時候不要自己做

這個技能是什麼

面對一個需求，有三種路徑：購買／使用現成產品、設定現有工具（含低程式碼與內建功能）、自建。FDE 的專長常是自建，但最好的答案常常不是自建。

為什麼 FDE 需要它

每一行自建的程式都是客戶未來要維護的負擔。FDE 離開後，誰來維護？如果現成工具能達到 80% 的效益，自建多出的 20% 通常不值得，除非那 20% 就是核心價值。誠實地建議「不要自己做」，是建立信任的一種方式。

怎麼做

判斷的問題

問題偏向自建偏向購買或設定
需求是否為客戶的核心差異化？是否（通用功能）
現成工具能否達到足夠的效益？不能能達到 80% 以上
資料與整合限制客戶環境特殊，現成工具接不上現成工具已支援客戶的系統
客戶的維運能力有工程團隊可長期維護沒有，需要供應商支援
資料不可出境／不可上雲必須自建或本地部署供應商能滿足合規
時程時間充裕要在短時間內看到效益

總擁有成本（TCO）的簡單檢查

  • 自建：開發 ＋ 長期維護 ＋ 升級（模型與框架一直在變）＋ 人員流動風險。
  • 購買：授權費 ＋ 整合 ＋ 被供應商綁定的風險（資料能否匯出？）。
  • 設定：最便宜，但受限於工具能力；先試，再決定是否自建。

混合路線

常見的好做法：用現成工具做通用部分，只自建客戶特有的整合與規則。例如客服工單用現成系統，自建的只是「分流規則與核可流程」。

業界情境

示意情境：客戶堅持自建文件問答

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：客戶的 IT 主管想自建一個內部文件問答系統，「因為可以完全掌控」。FDE 做了兩件事：

  • 用兩天用現成工具設定出一個原型，並用 30 題真實問題評估：達成率 82%。
  • 把結果與自建的估算（三個月開發、一位工程師長期維護）並列，並指出現成工具的缺口（權限過濾）可以用什麼方式補。

最後客戶選擇「現成工具＋小型自建的權限層」。FDE 沒有失去工作，反而因為建議誠實而得到後續專案。

常見錯誤

  • 因為自己會做，就預設要自建。
  • 低估維護成本，忘記模型版本與 API 會變。
  • 忽略資料能否匯出的鎖定風險。
  • 用「完全掌控」當理由，卻沒有維運能力。

非程式領域怎麼用

非程式領域版

同樣的決策出現在任何導入：買現成的流程範本、設定既有系統，還是自己設計？先試最便宜的路徑，並用事先定義的指標評估是否足夠。

怎麼練

  • 替你正在做的需求，寫一頁「自建、購買、設定」比較，並附上你的建議與理由。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 有一份比較，且至少有一次你建議「不要自建」，並被客戶採納或有合理的討論。

觸類旁通

Build-vs-buy 是所有技術決策的通則。它的真正問題是「這裡是不是我們的核心競爭力」，這在你自己的職涯決策（要自己做還是用現成的）也適用。
