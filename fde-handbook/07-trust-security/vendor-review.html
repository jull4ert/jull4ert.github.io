供應商與工具審查

模型服務、函式庫、外掛與 MCP 伺服器：進入客戶環境前要先審查

這個技能是什麼

供應商與工具審查是在引入外部的模型服務、軟體套件、外掛與 MCP 伺服器之前，評估它們對資料、安全與營運的影響。

為什麼 FDE 需要它

OWASP 的 LLM 清單也把「供應鏈」列為風險之一（LLM03）。你選用的每一個外部元件，都成為客戶環境的一部分；它的問題就是你的問題。FDE 常是選擇與引入這些元件的人，因此要有審查的習慣。

怎麼做

審查清單

面向問題
資料使用送出的資料是否被保存？多久？是否用於訓練？可否關閉？（以合約與官方政策為準，並留存版本與日期）
位置與子處理者資料處理在哪些區域？有哪些子處理者？
安全與認證有哪些安全認證與稽核報告？涵蓋的範圍是否包括你使用的產品？
事件通報發生事故時，供應商多久內通知？
可用性與支援服務水準、支援管道、已知的中斷紀錄
模型生命週期版本如何命名與下架？下架前通知多久？行為變更如何公告？
價格與限額價格變更機制；速率與用量限制；超限的行為
鎖定與退出資料能否匯出？換供應商的成本？你的程式有隔離介面嗎？
開源套件與外掛維護是否活躍？授權？已知漏洞？來源可信嗎？權限要求合理嗎？
MCP 伺服器誰寫的？原始碼可審查嗎？要哪些權限與網路存取？是否能固定版本？

審查的實務

  • 建立核准清單：客戶環境只能使用清單中的元件；新增要走流程。
  • 固定版本：不要使用「最新」；升級是一次有評測的變更。
  • 隔離與最小權限：外部元件只拿到它需要的權限與資料。
  • 定期重新審查：供應商條款、版本與漏洞會變動。
  • 退出計畫：知道如果某供應商不可用或政策改變，怎麼切換。

業界情境

示意情境：「好用的開源 MCP 伺服器」

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：團隊在網路上找到一個好用的 MCP 伺服器，可以直接連資料庫與雲端儲存。同事建議直接用在客戶環境。

  • FDE 先審查：作者不明、原始碼有一段會把查詢內容送到外部位址、權限要求是整個資料庫的讀寫。
  • 決定：不使用；改自行實作窄版本的工具，並請客戶審查程式碼。
  • 這是「供應鏈風險」的實際樣子：好用不代表可信。

常見錯誤

  • 因為方便就直接引入來源不明的套件。
  • 沒有固定版本。
  • 忽略模型下架或行為改變的風險。
  • 沒有退出計畫。

非程式領域怎麼用

非程式領域版

非程式情境：評估一個新的 AI 工具（如寫作、摘要服務）前，同樣要問：它如何處理上傳的資料？公司是否核准？員工能否用個人帳號？建議以核准清單管理。

怎麼練

  • 為 TicketDesk 使用的每個套件與外部服務，建立一張供應商審查表。
  • 挑選一個你想引入的第三方 MCP 伺服器或函式庫，完成上面的審查清單並寫出結論。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 有一份核准清單與供應商審查紀錄，且曾有至少一次因審查而拒絕或調整引入的元件。

觸類旁通
