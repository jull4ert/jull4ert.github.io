Lab 5：人機核可：後端強制與 Vue 介面

防線要放在後端；畫面只是讓人容易做對

目標：讓「需要人工」的來信，在核可時必須由人明確確認，並讓這個規則在後端被強制執行。

預估時間：90 分鐘　前置：Lab 0；了解 Razor 與 Vue 的 @ 衝突（請用 v-on:click）

步驟

  1. 在畫面上對 #5（客訴）按「AI 分流」，然後直接按「核可送出」。目前會發生什麼？
  2. 用瀏覽器開發者工具（或 curl）直接呼叫 POST /api/tickets/5/approve，確認即使不經過畫面也能送出。這說明了什麼問題？
  3. 修改後端：ApproveRequest 加入 Confirmed；需人工的案件若未確認，回傳 400。先寫測試。
  4. 修改 Vue：需人工的信顯示確認勾選框；未勾選時停用「核可送出」，勾選後送出 confirmed: true。
  5. 稽核紀錄加入 confirmed=。
  6. 思考：勾選框能不能被當成「人真的看過」的證據？有什麼方法能降低「一律勾選」的風險？（提示：見自動化偏誤）

預期結果

作者實測：

  • 三個單元測試通過（需人工且未確認 → 400；需人工且已確認 → 成功；一般案件不需確認）。
  • 以 curl 呼叫：未帶 confirmed → 回傳 {"error":"此信需要人工判斷，請確認後再核可"}；帶 confirmed:true → 成功，稽核紀錄出現 confirmed=True。
  • Vue 變更只做了 node --check 語法檢查，沒有在瀏覽器中實際點擊測試，請你自己驗證畫面行為。

檢核清單

  • 後端測試先於實作
  • 直接呼叫 API 也無法繞過
  • 畫面在未確認時停用按鈕
  • 稽核記錄確認狀態
  • 能說明勾選框的局限

參考解答

後端（TicketsApiController）

public record ApproveRequest(string? Reply, bool Confirmed = false);

// 在檢查回覆非空之後：
// 需要人工判斷的信，必須由人明確確認；這個檢查放在後端，不能只靠畫面上的勾選框
if (ticket.Triage.NeedsHuman && !request.Confirmed)
{
    return BadRequest(new { error = "此信需要人工判斷，請確認後再核可" });
}

測試

// ---- Lab 5：需人工的信，核可時必須明確確認（後端強制，不只靠畫面） ----
public class ApproveConfirmationTests
{
    private static (TicketsApiController Controller, ITicketStore Store) Build()
    {
        var store = new InMemoryTicketStore();
        var audit = new InMemoryAuditLog();
        var triage = new TriageService(new FakeLlmClient(), audit, TimeProvider.System);
        return (new TicketsApiController(store, triage, audit, TimeProvider.System), store);
    }

    [Fact]
    public async Task Needs_human_ticket_cannot_be_approved_without_confirmation()
    {
        var (c, store) = Build();
        await c.Triage(5, default); // 客訴：一定需要人工
        var result = c.Approve(5, new TicketsApiController.ApproveRequest("我們很抱歉", false));
        Assert.IsType<BadRequestObjectResult>(result);
        Assert.Equal(TicketStatus.Triaged, store.Get(5)!.Status);
    }

    [Fact]
    public async Task Needs_human_ticket_can_be_approved_with_confirmation()
    {
        var (c, store) = Build();
        await c.Triage(5, default);
        var result = c.Approve(5, new TicketsApiController.ApproveRequest("我們很抱歉", true));
        Assert.IsType<OkObjectResult>(result);
        Assert.Equal(TicketStatus.Replied, store.Get(5)!.Status);
    }

    [Fact]
    public async Task Routine_ticket_does_not_need_confirmation()
    {
        var (c, _) = Build();
        await c.Triage(3, default); // 技術問題，信心高，不需人工
        var result = c.Approve(3, new TicketsApiController.ApproveRequest("請提供截圖", false));
        Assert.IsType<OkObjectResult>(result);
    }
}

關於勾選框的局限

  • 勾選框只是留下「責任歸屬」的紀錄，並不能保證人真的看過。
  • 可以搭配：高風險類別要求輸入簡短理由、定期插入已知有誤的測試案例、抽樣審查與覆寫率監控。
