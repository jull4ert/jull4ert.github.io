相鄰技術

RPA、低程式碼、BI、規則引擎、OCR、傳統機器學習：何時不用 LLM

這個技能是什麼

LLM 不是唯一的工具。許多客戶問題用其他技術更便宜、更穩定、更容易維護。FDE 要知道這些選項，並誠實地建議最合適的一個。

為什麼 FDE 需要它

Anthropic 對 agent 的建議也是「從最簡單的解法開始」。熟悉相鄰技術，才能做到這件事，也才能與客戶既有的工具共存，而不是推翻重來。

怎麼做

技術適合不適合（或較弱）與 LLM 的搭配
規則引擎／一般程式規則完全確定、需要 100% 一致規則模糊、文字理解LLM 理解輸入，規則決定結果（TicketDesk 的做法）
RPA（機器人流程自動化）固定的畫面操作、沒有 API 的舊系統輸入多變、需要理解文字LLM 先整理輸入，RPA 執行重複操作；注意脆弱性
低程式碼／表單／工作流平台簡單流程、審核與通知複雜的判斷與文字處理LLM 作為其中一個步驟（分類、草稿）
BI／儀表板看趨勢、監控、指標個案層級的處理用於監控 AI 專案（覆寫率、成本）
全文搜尋關鍵字查文件語意相近但用詞不同的查詢檢索階段可結合搜尋與語意檢索
OCR／文件處理服務掃描文件轉文字與版面理解文字內容先 OCR，再由 LLM 擷取與摘要；注意品質核對
傳統機器學習有大量標註資料的預測與分類、需要可預期的成本資料少、任務常變分類量大且穩定時，可能比 LLM 便宜且快
人工流程改善流程本身有問題—先修流程，再談自動化

選擇時的問題

  • 這個問題的規則是否確定？（是 → 程式）
  • 有沒有大量穩定的標註資料？（是 → 考慮傳統機器學習）
  • 輸入是多變的文字嗎？（是 → LLM 有價值）
  • 客戶已經有這類工具嗎？（是 → 優先使用，減少維運負擔）
  • 失敗時的後果與可解釋性要求？

業界情境

示意情境：一個其實不需要 LLM 的專案

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：客戶想用 LLM 判斷「請假單是否符合規定」。FDE 檢視後發現：規則共十二條，全部確定（天數、職等、日期區間）。

  • 建議：用規則引擎實作；請假單上的「事由」文字，可選用 LLM 做摘要，但不參與決定。
  • 客戶一開始失望，但在兩週後看到「100% 一致、可稽核、零模型成本」後接受。
  • 這個建議也避免了一個潛在的稽核問題：AI 無法解釋為何某張單據被拒。

常見錯誤

  • 看到問題就想用 LLM。
  • 忽略客戶已有的工具。
  • 把 RPA 當成長期穩定的方案而不評估維護成本。

非程式領域怎麼用

非程式領域版

非程式專案中，簡單的表單、檢核表與流程調整，常常比導入任何技術更有效。先問：「如果不用任何新技術，我們能怎麼改善？」

怎麼練

  • 替你正在考慮的 AI 題目，各列出一個「不用 LLM」的替代方案，比較成本與風險。
  • 找出客戶現有的一個自動化工具，想想 LLM 怎麼與它搭配。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 在至少一個專案中，你曾建議「不用 LLM」或「LLM 只負責其中一步」，並有理由。

觸類旁通

觸類旁通

「用對的工具」是所有技術職務的核心判斷；了解工具的邊界，比精通單一工具更能解決真實問題。
