回歸測試

每次修改都重跑評測，追蹤歷史，避免「修好一個、壞掉三個」

這個技能是什麼

回歸測試是在每次變更後，重新執行固定的測試與評測，確認既有的表現沒有變差。對 AI 系統，變更包含：提示、模型版本、規則、資料、程式。

為什麼 FDE 需要它

AI 系統特別容易發生「局部改善、整體退化」：為了修好一類錯誤，改了提示，卻讓另一類錯誤變多。沒有回歸，你只會在客戶抱怨時才發現。

怎麼做

做法

  • 把評測放進一般的測試流程：TicketDesk 的評測就是 xUnit 測試，dotnet test 就會執行。
  • 任何會改變輸出的修改（提示、模型、規則、資料前處理）都要跑評測，並把結果寫進變更說明。
  • 設定門檻：品質低於門檻、或任何安全底線失敗，就讓建置失敗。
  • 記錄歷史：每次評測的版本、日期、指標，畫成趨勢；看得到緩慢的退化。
  • 保留集不隨意使用，避免過度配合。

在 TicketDesk 中

Assert.Empty(unescalated);                       // 安全底線：不能有漏掉的
Assert.True((double)correct / total >= 0.70,     // 品質門檻（目前基準約 78%）
            "dev 正確率低於 70%");

真實模型的特別注意

  • 非確定性：相同輸入可能得到不同輸出。降低隨機性的設定能幫助一致，但不一定完全相同；重要的評測要多跑幾次取平均，並觀察變異。
  • 固定模型版本：使用供應商允許的固定版本識別，並記錄；模型更新就是一次必須回歸的變更。
  • 成本：評測也花錢。小型快速評測每次提交都跑；完整評測每日或發版前跑。
  • 替身與真實並用：替身用於每次提交（快、免費）；真實模型用於發版前與定期。

CI 範例（概念示意，未於本手冊實測）

# 以 GitHub Actions 為例的概念：每次 PR 跑測試與評測
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-dotnet@v4
    with: { dotnet-version: '8.0.x' }
  - run: dotnet test TicketDesk.sln

實際的版本號與語法請以你所用平台的官方文件為準。

業界情境

示意情境：改善語氣，卻漏掉升級

以下是虛構的組合情境，用來說明做法；人名、公司與數字都是示意，不是真實客戶。

虛構情境：為了讓草稿更親切，有人修改了提示。因為沒有回歸，一週後才發現：在特定句型下，模型不再給出較低的信心值，使幾封應該升級給人的信件被放行。

  • 有回歸：該次修改在 PR 階段就會讓「應升級」的案例失敗，被攔下。
  • 之後把這幾封信加進評測集，成為永久的保護。

常見錯誤

  • 只在最初驗收時評測，之後再也不跑。
  • 修改後只看被修的那一類。
  • 評測結果沒有歷史，無法看趨勢。
  • 模型更新時沒有跑回歸。

非程式領域怎麼用

非程式領域版

非程式專案也應該有回歸：提示範本更新後，用固定的 20 份樣本重跑，檢查重要欄位是否仍正確，並留下紀錄。

怎麼練

  • 在 TicketDesk 把門檻調到 0.85，觀察測試失敗；再想想要怎麼改善而不是調回門檻。
  • 建立一份評測歷史表：日期、變更內容、正確率、底線結果。

可觀察的證據

用這些證據判斷自己是否真的會了，而不是「看過」。

  • 每一次變更都有對應的評測紀錄；曾有至少一次回歸測試攔下了有問題的變更。
