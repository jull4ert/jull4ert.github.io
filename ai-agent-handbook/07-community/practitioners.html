實踐者長文三篇

三位有經驗的開發者各自的工作方式：個人化強，重在思考方式而非照抄指令。

本頁為 2026-11-11 閱讀原文後的重點整理（以自己的話改寫，僅引用極短片語）。原文可能已更新或修訂，採用前請回到原文確認。

1. Armin Ronacher：Agentic Coding Recommendations

Agentic Coding Recommendations

來源：個人部落格；作者 Armin Ronacher；2025-06-12。

重點

  • 把 agent 能觀察或操作的一切都當成工具，要求工具快、錯誤訊息清楚、能防誤用。
  • 服務輸出寫到 agent 讀得到的檔案，並避免服務被重複啟動。
  • 工具與 log 輸出要精簡：冗長會耗 Token、拖慢迴圈。
  • 寫「最笨但能動」的簡單程式：偏好函式勝於類別、避免繼承、直接用 SQL。
  • 重要的檢查（例如權限檢查）放在 agent 看得到的程式路徑，不要藏在別的檔案或設定。
  • 依賴升級要比以前更保守，能產生程式碼就少加依賴。
  • 為平行的 agent 設計：共享狀態（檔案系統、資料庫）要先想好如何隔離。
  • 程式庫大到超出 agent 能掌握的情境量時，就重構（例如抽出元件庫）。

可以直接套用

  • 把常跑的操作寫成腳本或 Makefile 指令，讓 agent 呼叫，而不是多裝一個工具 → 見 03 MCP
  • 輸出精簡與 log 寫檔 → 04 實作的省 Token
  • 簡單、局部化的程式碼其實也讓審查更容易 → 05

作者自己說的限制

  • 他以別名使用 claude --dangerously-skip-permissions（跳過權限詢問），並自述「有風險」，建議用 Docker 管理；這是個人在特定環境的選擇，不是本手冊的建議，見 09 權限與防護。
  • 作者預期文章「會很快過時」，並說這是個人工作流程，不是 Claude Code 的廣告。
  • 他幾乎不用 MCP，僅在替代方案太不可靠時才用；平行化他也自承還沒有好的解法。

2. Simon Willison：Designing agentic loops

Designing agentic loops

來源：個人部落格；作者 Simon Willison；2025-09-30。

重點

  • 挑「成功標準明確、需要大量嘗試錯誤」的問題：除錯、查詢優化、依賴升級、縮小容器等。
  • 好的自動化測試是放大 agent 價值的關鍵。
  • 傾向把工具設計成 shell 指令，並在 AGENTS.md（或同類檔案）記錄可用的 CLI 與使用範例。
  • 要讓 agent 無人值守地跑，須在受限的沙箱內：限制檔案、機密與網路。
  • 偏好在拋棄式的雲端容器（別人的電腦）上執行，並限制可連網的主機清單。
  • 給 agent 測試或預備環境的憑證；任何能花錢的憑證都要設定嚴格預算上限。

可以直接套用

  • 以測試與成功標準設計迴圈 → 04 實作、05 用證據收斂
  • 無人值守的隔離、憑證與預算 → 06 Headless 與 CI、09、成本控管

作者自己說的限制

  • 作者明說無人值守的跳過權限模式很危險：可能刪改資料、外洩機密、被當跳板攻擊；並引用「AI agent 就是在迴圈裡破壞環境的 LLM」這類說法。
  • 他對內建沙箱仍持保留，認為尚未看到足以信任的文件。
  • 他稱此領域「還很新」，並非每個問題都適用此模式。

3. Harper Reed：My LLM codegen workflow atm

My LLM codegen workflow atm

來源：個人部落格；作者 Harper Reed；2025-02-16。

重點

  • 先用對話式 LLM 把想法磨成規格，存成 spec.md，再動手。
  • 把規格交給推理模型產出計畫，切成小塊，每塊對應一個後續提示。
  • 計畫存 prompt_plan.md、清單存 todo.md，讓不同工作階段能接力、勾選。
  • 一次執行一個提示、跑測試，通過再往下。
  • 既有專案不是為整個專案規劃，而是每個任務各自規劃。
  • agent 的工作放在新分支；並隨時對照計畫文件，避免進度跑得比你的理解還快。

可以直接套用

  • 規格、計畫檔、待辦清單的接力方式，與 04 的流程幾乎一致 → 04 需求到程式碼
  • 用審查、補測試的提示審計既有程式碼 → 05

作者自己說的限制

  • 作者說這套做法「兩週後大概就不管用了」，所用工具與模型已過時，提示自述「又舊又破」。
  • 主要是單人工作流程；多人或多個 bot 並行時會互相衝突。
  • 他常「滑太快」而失控，所以靠測試與規劃來約束。
