權限與核准

agent 能做事，所以要決定它「能做到哪、誰按確認」。

三層動作，三種風險

層級範例風險建議
唯讀讀檔、搜尋、查行事曆低（但仍可能讀到機密）可放寬
可還原的修改編輯程式（有 git）、建立草稿中檢視 diff 後接受
難以還原 / 對外刪檔、force push、寄信、改他人行事曆、移動 Trello 卡片、部署高每次人工核准

核准的做法

  • 預設逐次詢問：初期保持，邊用邊學它會做什麼。
  • 白名單：把確定安全且重複的指令（如 git status、跑測試）設為免詢問。
  • 計畫模式：先只讓它規劃不動手，你看過計畫再放行。
  • 版本控制當保險：程式碼一律在 git 下作業，改壞可退回。

非程式工作要更小心

行事曆、信件、Trello 沒有 git 可退。建議：先讓它「只讀 + 提出建議清單」，確認後才開寫入；對外可見的動作（邀請與會者、發訊息）永遠人工確認。

機密

不要把密碼、金鑰、客戶個資直接貼進對話；用環境變數或祕密管理，並限制 agent 可讀的資料夾。詳見 06 治理。
