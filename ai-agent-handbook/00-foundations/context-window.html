情境視窗與分段交付

agent 的「工作記憶」有限，這決定了你該怎麼拆任務。

什麼是情境（context）

Agent 每一步「看得到」的內容：你的指令、對話歷史、它讀過的檔案、工具輸出。這些都計入有上限的 token 額度。

為什麼重要

  • 越長越雜：對話很長、讀了很多無關檔案後，品質會下降，早期的要求容易被忽略。
  • 系統會壓縮：過長時舊內容會被摘要，細節可能流失。
  • 換對話 = 失憶：新對話不記得上一段，除非寫進檔案（CLAUDE.md、規格書、memory）。
  • 成本與速度：情境越大越慢、越貴。

實務做法

原則怎麼做
一個對話一件事任務完成就開新對話，不要把所有事塞同一串
重要決定寫成檔案規格、決策、待辦存成 .md，下次讓 agent 讀
指定範圍「只看 src/Orders 資料夾」比「看整個專案」好
大型探索交給 subagent讓它在獨立情境搜尋，只回傳結論（Lv4）
分段交付需求 → 規格 → 實作 各階段各自驗收，再往下
經驗法則：當你發現要重複交代同一件事第二次，就該把它寫進檔案。

省 Token 技巧

Token 是計費與情境上限的共同單位。先理解錢花在哪，後面各區的省法才有依據。

花費來源說明怎麼降
每一輪都重送的歷史對話越長，每次回應都要把前面全部再讀一次（雖有快取折扣，仍是主要成本）任務完成就 /clear；換主題就換對話
讀進來的檔案讀過的檔案內容會留在情境裡只讀需要的檔案與範圍；大型探索交給 subagent
工具輸出測試、建置、log 的長輸出都會進情境過濾輸出，只留錯誤與摘要
常駐內容CLAUDE.md、已連接的 MCP 工具定義、skill 描述每次都在精簡常駐文件；停用用不到的 MCP
輸出與重做方向錯了重做，等於付兩次錢先用計畫模式確認方向，再動手

先量測，再優化

  • /context：查看目前情境被什麼佔用（對話、檔案、MCP 工具、系統提示等）。
  • /cost：查看本次對話的用量（訂閱方案與 API 方案顯示內容不同）。
省 Token 與品質常常同向：情境越乾淨，agent 越專注。但不要為了省而省，反覆重做的成本遠高於多讀一個檔案。
