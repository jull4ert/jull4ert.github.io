過度信任的警訊與信任階梯

新手最容易發生的風險是「太快相信」。這一頁教你辨認警訊，並一步步放權。

新手常見的過度信任

現象為什麼危險對策
看到「已完成、測試通過」就合併agent 可能沒有真的執行，或測試本身沒有保護力要求貼出實際輸出；自己再跑一次
不看 diff可能被多改、被刪除檢查每次都看 --stat 與內容
接受自己不懂的做法出事時不會查要它解釋，或換更簡單的寫法
把機密、個資貼進對話資料外洩見 09 資料與機密
對 agent 的「為什麼」照單全收解釋也可能是編的用測試、文件、原始碼查證
一次要太多東西產出太大，根本沒辦法審拆成小任務，每個都能獨立驗收

你已經過度依賴的訊號

  • 你不再讀 diff，直接接受。
  • 出錯時，你只會把錯誤丟給 agent，不知道從哪裡查起。
  • 你說不出程式「為什麼這樣寫」。
  • 驗證都靠 agent 自己回報。

出現這些訊號時，放慢：回到小任務、親手跑測試、自己寫一段。

信任階梯：一級一級放權

級別你讓 agent 做升級條件
L0 唯讀讀程式、回答問題、解釋錯誤能判斷它的回答是否正確
L1 小修改單一檔案、單一函式的修改，你逐行審連續 5 次 diff 你都看得懂
L2 功能實作一個完整小功能，含測試，你看證據表能自己寫出驗收條件與測試
L3 交叉審查多個 agent 審查，你裁決能分辨審查意見的真偽
L4 自動化排程、CI、批次任務（唯讀為主）已有穩定的規範與驗證

升級要有證據，不是感覺。不同風險的任務可以停在不同級別：金流、權限、資料庫結構，建議停在 L1 或 L2，並多一個人審查。

向同事交代你的產出

在 PR 說明中，誠實說明哪些是 agent 產出、你做了哪些驗證。例如：

## 驗證
- 先寫失敗的測試（Cancel_ShippedOrder_Fails），確認失敗後修正，通過
- 執行全部測試：10 通過、0 失敗
- 手動操作：已出貨訂單按取消，畫面顯示錯誤訊息
## AI 輔助
- 實作與測試由 agent 產生；我逐行審過 diff
- 我不確定的部分：錯誤訊息的文案，請確認

這樣審查者知道該把注意力放在哪，也建立你的可信度。

一定要找人的時候

  • 權限、金流、個資、migration。
  • 你看不懂但 agent 很堅持的做法。
  • 改動範圍比預期大很多。
  • 你已經和 agent 來回超過 30 分鐘沒有進展。
