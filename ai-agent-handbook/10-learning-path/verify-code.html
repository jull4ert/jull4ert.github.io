驗證看不懂的程式

你不可能全部看懂 agent 寫的東西。這一頁教你在看不懂時，如何確認它是對的。

原則只有一條：你不需要立刻看懂每一行，但你必須有辦法證明它是對的；證明不了，就不要提交。

五步驗證法

步驟做法你得到什麼
1. 看範圍git diff --stat：動了哪些檔案？有沒有不該動的？知道影響面
2. 要它解釋請 agent 逐段解釋，並列出這段改動的前提假設把「看不懂」變成具體的疑問
3. 用測試證明執行既有測試；沒有測試就先請它補，並確認測試先失敗客觀證據
4. 自己試一次實際操作功能，或改一個輸入預測結果再驗證自己的理解
5. 找人看不確定的部分，標記出來問同事，附上你已經驗證的證據補上你的盲點

讓 agent 把程式講清楚

> 請逐段解釋 @src/OrderDemo.Web/Services/OrderService.cs 的 Cancel 方法：
> 1. 每一段在做什麼，用一句話
> 2. 如果 orderId 不存在會發生什麼？如果 departmentId 不符呢？
> 3. 這段程式有哪些前提假設？
> 4. 你認為最可能出錯的三個地方
> 用我這個初學者能懂的方式，不要貼大段程式碼。
> 我的理解是：「Cancel 只要訂單存在就會把狀態改成已取消」。
> 請指出我理解錯誤或遺漏的地方，並給一個會讓我的理解出錯的具體例子。

第二種（你先講、它來糾正）特別有效：它逼你把理解說出來，agent 才找得到落差。

用「預測再驗證」建立理解

  1. 看一段邏輯，先自己預測「輸入 X 會得到 Y」。
  2. 寫成測試或實際執行。
  3. 預測錯了，代表你的理解有洞，回頭問 agent 為什麼。

程式碼警訊清單（看到就停下來問）

警訊為什麼要小心
catch (Exception) 然後回傳預設值會吞掉所有錯誤，問題被藏起來
寫死的數字、帳號、路徑、網址換環境就壞；可能含機密
測試只斷言「不是 null」或沒有斷言測試幾乎一定通過，沒有保護力
為了讓測試通過而修改測試可能掩蓋真正的錯誤
刪除了你沒要求的程式或檢查可能拿掉了防線
忽略 await、沒有釋放資源（IDisposable）非同步與資源的 bug 很難重現
使用者輸入直接拿來信任（例如 departmentId 來自查詢字串）授權與安全問題
前端 v-for 沒有 key、直接改 props畫面更新異常

必須找人看的情況

  • 涉及權限、金流、個資、資料庫結構變更（migration）。
  • 你無法用測試或實際操作證明它正確。
  • agent 很堅持某個做法，但你覺得怪。
  • 改動超出你本來要改的範圍。

提交前的自問

  • 我能不能用自己的話向同事說明這個改動？
  • 我有沒有親眼看到測試先失敗、後通過？
  • 我有沒有實際操作過這個功能？
  • diff 裡有沒有我不認得的檔案或改動？
