把 agent 當老師

同樣一個工具，可以替你代工，也可以教你變強。差別在你怎麼問。

新手最大的陷阱，是用 agent 只求「完成」，卻沒有學到東西，下次還是不會。這一頁教你把 agent 變成老師，讓工作和學習同時發生。

三種使用姿態

姿態怎麼問學習效果
代工「幫我做 X」低：你只拿到結果
家教「先解釋 X 怎麼做，再讓我試試」高
審稿人「我先做了 X，請你找出問題」最高：你先動腦，再被糾正

建議的比例：日常任務可以用代工；但每天至少有一個任務用家教或審稿人的方式做。

常用的學習提示

讀懂專案

> 我是剛接手這個專案的新人。請帶我導覽：
> 1. 用 5 句話說明整體架構
> 2. 從使用者按下『取消』按鈕開始，列出經過的檔案與方法
> 3. 最值得先讀的三個檔案，以及原因

解釋錯誤

> 我執行 dotnet test 得到下面的錯誤（貼上）。
> 請先解釋這個錯誤的意思與可能原因，列出 3 個我可以自己檢查的方向。
> 現在先不要修改任何檔案。

蘇格拉底式引導

> 我想自己修這個 bug。請不要直接給答案，
> 用提問引導我：先問我預期行為，再問我實際行為，再問我認為哪裡出問題。

比較兩種寫法

> 這裡可以用 foreach，也可以用 LINQ。請各給一個版本，
> 比較可讀性與效能，並說明在這個專案的慣例下建議哪一個。

出練習題

> 依這個專案的程式，出 3 題難度遞增的練習，
> 讓我練習 xUnit 測試。先不要給解答，我做完再請你批改。

先寫後審

> 我寫了這個方法（貼上或 @檔案）。請以資深審查者的角度，
> 指出問題與可改進之處，依嚴重度排序，並解釋原因。

先自己試 15 分鐘

遇到問題，建議先自己嘗試 15 分鐘：查錯誤訊息、看程式、做出假設。再去問 agent，並把你的假設一起帶上，這樣學到的最多。若 15 分鐘完全沒頭緒，就直接問，不要硬撐。

學習日誌

每天用 5 分鐘寫下三件事：

  • 今天讓 agent 做了什麼。
  • agent 哪裡做錯或讓我意外。
  • 我新學到的一個觀念或做法。

一週後回頭看，你會發現自己重複犯的錯，這些就是該寫進 CLAUDE.md 或自己多練習的主題。

避免的壞習慣

習慣後果
錯誤訊息一出現就整段丟給 agent，不看永遠看不懂錯誤訊息
只複製貼上，不理解無法維護、無法除錯
agent 說對就當對被錯誤自信帶著走
完全不寫測試，靠「跑起來沒錯」之後改動會壞掉而不自知
