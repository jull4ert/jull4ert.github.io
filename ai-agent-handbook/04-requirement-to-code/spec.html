② 規格撰寫

把訪談結果整理成可驗收的規格，這份文件是後面所有階段的依據。

規格的作用

  • 實作的依據、測試的依據、審查的依據。
  • 讓換了對話的 agent 也能完整接手。
  • 交接與日後維護時，回答「當初為什麼這樣做」。

範本

# 訂單列表篩選
## 目標
客服人員可依狀態與日期快速找到訂單。
## 非目標
- 不做匯出；不改權限模型；不做模糊搜尋。
## 使用情境與驗收條件
1. 依狀態篩選
   - Given 存在多種狀態的訂單
   - When 選擇「已出貨」
   - Then 只顯示已出貨訂單，筆數與條件一致
2. 日期區間（建立日期、出貨日期可同時選，AND 條件）
3. 無符合資料：顯示「查無資料」，保留已選條件
## 邊界與錯誤
- 起日大於迄日：顯示欄位錯誤，不送出查詢
- 跨部門訂單：維持現有權限過濾，不可見
- 資料量：10 萬筆內，回應 < 2 秒
## 影響範圍
- OrderQuery、OrderListController、列表前端元件
## 未決問題
- 是否需要記住使用者上次選擇的條件？（待確認）

請 agent 產出規格

> 依 @docs/specs/order-filter-decisions.md 撰寫規格 docs/specs/order-filter.md，
> 格式參考 @docs/specs/_template.md。
> 要求：
> - 每個情境都有可驗證的驗收條件（Given/When/Then）
> - 只能使用決策紀錄中的內容，不確定的寫進「未決問題」
> - 明確列出非目標

好的驗收條件長什麼樣

不好好
篩選要快10 萬筆資料下，套用篩選後 2 秒內顯示結果
錯誤處理要完善起日大於迄日時顯示「起日不得晚於迄日」，且不發出請求
介面要好用篩選條件在重新整理頁面後仍保留於網址參數

判斷標準：能不能直接寫成一個測試。寫不成測試的描述，就還不夠具體。

關卡：需求審查

規格完成後，在動手前先做一次需求審查（見 05 需求審查）：事前驗屍、反方角色、缺漏情境。把發現的問題回寫進規格，再進入下一階段。這是整條流程中投資報酬率最高的一步。

讓規格成為專案的一部分

  • 放進版本控制（docs/specs/），與程式碼一起審查、一起演進。
  • CLAUDE.md 加一行索引，讓之後的任務知道去哪找（見 02 規格、ADR 與術語表）。
