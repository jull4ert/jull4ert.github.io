把成果整理成別人看得懂、可安全合併的形式，並更新該更新的文件。

項目內容

Commit message

> 依目前的 git diff 寫 commit message。
> 格式：第一行 50 字內摘要；空一行；說明為什麼要改、影響什麼。
> 只寫 diff 中確實存在的內容，不要推測。

若你有慣用的格式（語言、前綴），做成 skill，之後一句話觸發（見 02）。

PR 說明範本

## 背景
客服需要快速找出特定狀態與日期的訂單。規格：docs/specs/order-filter.md
## 變更
- OrderQuery 新增狀態、日期區間條件
- API 加入參數驗證（起日大於迄日回 400）
- 前端新增篩選元件，條件同步至網址
## 如何驗證
- 單元／整合測試全數通過（附輸出）
- 手動走過規格情境 1～3（附截圖）
## 風險與回滾
- 10 萬筆資料下查詢約 1.8 秒；已加索引（見 migration）
- 回滾：還原此 PR，索引可保留
## 審查紀錄
- 交叉審查 2 輪；已證實 2 項已修正，1 項建議駁回（理由見討論）

給非技術者的摘要

> 依這個 PR 的變更，寫一段給客服主管看的白話說明：
> 新增了什麼操作、怎麼用、有哪些限制。不要出現程式術語。

合併前最後確認

  • 規格狀態改為「已實作」，未決問題都有結論。
  • 計畫檔任務全部勾選，或明列未完成與原因。
  • 合併決定由你下，agent 不自行合併或部署。

省 Token 技巧

  • Commit 與 PR 說明基於 diff 生成，並要求「只寫 diff 中存在的內容」，避免長篇推測。
  • 範本化：PR 範本與 commit 格式做成 skill，一句話觸發，不必每次貼指令。
  • 交付前 /clear：整理文件不需要實作時的完整歷史，讀 diff 與計畫檔即可。
