④ 實作

一次一個任務，先寫測試，再寫程式；小步前進、隨時可退回。

每個任務的迴圈

開新對話（/clear） → 讀規格 + 計畫 + 本任務 │ ▼ 紅：先寫會失敗的測試（對應驗收條件）→ 執行，確認失敗 │ ▼ 綠：寫最少的程式讓測試通過 → 執行，確認通過 │ ▼ 整理：重構、對齊專案風格 → 測試仍全綠 │ ▼ 你看 diff → commit → 在計畫檔勾選 → 下一個任務

起手提示

> 請執行 @docs/plans/order-filter.md 的任務 2。
> 規格見 @docs/specs/order-filter.md。
> 做法：
> 1. 先寫對應驗收條件的測試，執行並確認它們會失敗
> 2. 再實作，讓測試通過
> 3. 沿用 @src/Orders/OrderQuery.cs 現有的寫法
> 4. 只做任務 2，不要順手處理其他任務
> 完成後貼出測試輸出，並列出改動的檔案

為什麼先寫測試

  • 測試把「驗收條件」變成程式能檢查的東西，agent 才有明確的完成標準。
  • 測試先失敗，能證明它真的在測那件事，而不是寫成必過。
  • 後續重構與審查有保護網。

讓它走在軌道上

狀況做法
它開始改計畫外的檔案Esc 中斷：「只改任務範圍內的檔案，其他的還原」
測試不過，它改測試來配合明確要求：「不得修改既有測試來讓它通過；若認為測試有誤，先告訴我原因」
卡住反覆嘗試要求停下來回報：已試過什麼、卡在哪、你的假設；必要時退回重來
寫法與專案不一致指定參考檔案，或補進 CLAUDE.md 慣例
做到一半對話太長commit 目前進度，/clear，用計畫檔接續

小步提交

每完成一個任務就 commit。壞了可以精準退回，審查也只需看一小段 diff。請 agent 依 diff 寫 commit message（見「交付」）。

平行任務

互不相依的任務，可用 git worktree 各開一個對話同時進行（見 06 進階工作流程），完成後合併。相依的任務不要平行，以免衝突。

你的抽查重點

  • diff 是否只包含該任務的檔案。
  • 測試是否真的對應驗收條件，而非只測 happy path。
  • 有沒有寫死的值、被註解掉的程式碼、過度設計。

省 Token 技巧

  • 一任務一對話：完成、commit 後 /clear，再用計畫檔接續。
  • 只跑相關測試：dotnet test --filter OrderTests，全部測試留到驗證階段。
  • 過濾輸出：要求「只回報失敗的測試與錯誤訊息」，不要貼完整輸出。
  • 給參考檔案：「寫法參考 @某檔案」，免去它搜尋風格的成本。
  • 卡住就停：設定「同一問題嘗試 3 次未果就回報」，避免無底洞式重試。
  • 簡單任務用較小模型：機械性修改（改名、補欄位）不必動用最大的模型。
