需求到程式碼

從一句模糊的需求，到可上線的程式碼：每一階段都由 agent 代勞，你只在關卡做決定。

把整件事拆成六個階段，每個階段產出一份檔案，下一階段讀這份檔案，而不是依賴冗長的對話記憶（見 Lv0 的情境視窗）。你在每個關卡確認後才往下。

總覽

一句話需求 │ ① 訪談 agent 反問，你回答 → docs/specs/xxx-decisions.md ▼ │ ② 規格 整理成可驗收的規格 → docs/specs/xxx.md ▼ ◄── 關卡：需求審查（05） │ ③ 拆解 設計 + 切成小任務 → docs/plans/xxx.md（含任務清單） ▼ ◄── 關卡：你審計畫 │ ④ 實作 一次一個任務，先測試 → 程式碼 + 測試 ▼ │ ⑤ 驗證 實際跑起來、對照驗收條件 → 證據報告 ▼ ◄── 關卡：程式碼審查（05） │ ⑥ 交付 commit、PR、文件更新 → 可合併的 PR

六個階段頁面

每個階段的「你」與「agent」

階段agent 做你做
訪談提問、指出矛盾、給建議答案回答、做取捨
規格整理成文件、列出未決問題確認是你要的
拆解探索程式碼、提出設計與任務選方案、核准計畫
實作寫測試與程式、自我檢查抽查 diff
驗證跑測試、啟動、截圖、對照條件看證據、親自試用關鍵流程
交付寫 commit、PR 說明、更新文件決定是否合併

幾個貫穿全程的習慣

  • 階段之間換對話：用 /clear 開新對話，開頭只引用上一階段的檔案。
  • 檔案是事實來源：口頭改的決定要回寫進檔案，否則下次就消失。
  • 先計畫模式、後動手：訪談、規格、拆解都在唯讀的計畫模式完成。
  • 留下可回溯的紀錄：決定、取捨、被否決的方案，之後才查得到為什麼。
本區的流程是一種建議的做法，可依任務大小裁剪：小修改可以直接跳到實作，大功能才需要完整走完。
