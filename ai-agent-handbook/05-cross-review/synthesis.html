整合與裁決

多方意見匯整後，由你決定哪些處理、哪些駁回，並讓盲點不再重複。

彙整流程

  1. 收集：各審查者的原始輸出，保留不改。
  2. 去重：合併描述不同但指向同一問題的發現；多人同時提到，信心上調。
  3. 驗證：對高嚴重度或有爭議的項目要求證據（見「用證據收斂」）。
  4. 排序：依影響、發生機率、修復成本排序。
  5. 裁決：採納／延後／駁回，並寫下理由。
  6. 回饋：把重複出現的盲點寫進規範或審查 skill。
> 以下是 3 位審查者的輸出（貼上或 @檔案）。請彙整：
> 1. 合併重複項，註明有幾位提出
> 2. 每項標示狀態：已證實／可能成立／推測
> 3. 依「影響 × 機率」排序，並估計修復成本（小/中/大）
> 4. 彼此矛盾的意見單獨列出並說明分歧點
> 不要替我做決定，只整理成裁決表。

裁決表

#發現狀態嚴重度修復成本決定理由
1已出貨訂單可取消已證實高小採納測試重現，違反規格 §3.2
2查詢缺少索引推測中中延後目前資料量小，列入觀察
3建議改用策略模式推測低大駁回屬風格偏好，現況可讀

採納準則

  • 已證實且影響高：一律修。
  • 涉及安全、金錢、個資、資料遺失：門檻放低，推測也要追查。
  • 純風格偏好：以專案規範為準，規範沒寫就不採納。
  • 多位審查者獨立提出同一點：提高優先序。
  • 修復成本遠大於風險：記錄為已知風險而不是硬修。

什麼時候停

設定收斂規則，避免無止盡循環：「連續一輪沒有新的『已證實』高、中嚴重度問題，就結束」。通常 1～2 輪即可，再多多半是雜訊。

讓盲點不再重複

盲點類型寫到哪
專案特有規則（例如查詢一律走 Query 物件）CLAUDE.md 的慣例／禁忌
每次審查都要檢查的項目審查 skill 的檢查表
需求常漏的情境規格範本的「缺漏情境」章節
已做的重大取捨ADR，避免被重複挑戰

把整套流程做成 skill

description: 對需求規格或程式碼變更進行交叉審查。當使用者要求交叉審查、找盲點、完整 review 時使用。
---
# 交叉審查流程
1. 確認審查對象（規格檔或 git diff）與比對基準。
2. 啟動獨立 subagent：需求用 spec-reviewer；程式碼用 code-reviewer，
   依需要平行啟動正確性、安全、測試三個視角。
3. 對高、中嚴重度發現，派另一個 subagent 嘗試反駁並要求證據。
4. 彙整成裁決表（狀態、嚴重度、修復成本、建議），交由使用者決定。
5. 使用者決定後才開始修改；修完重新執行失敗測試確認。
不得自行跳過裁決直接修改程式碼。
流程中「由使用者裁決」是刻意設計：交叉審查降低盲點，不取代責任。

省 Token 技巧

  • 收斂規則就是預算：連續一輪沒有新的已證實高、中嚴重度問題就停，不無限循環。
  • 彙整時只傳摘要：審查者的原始長輸出存檔，彙整對話只讀各自的發現清單。
  • 把重複盲點寫進規範：同一類問題一次寫進 CLAUDE.md 或審查 skill，之後不必每輪再審。
  • 裁決由你決定：避免讓 agent 自己再多輪討論。
