品質評估

不要憑感覺判斷 agent 好不好用；用小而持續的量測看出改善或退步。

為什麼要評估

agent 的輸出常常「看起來對」。若沒有量測，你不知道換了模型、改了 CLAUDE.md、加了 skill，結果是變好還是變壞，也不知道自己是不是越來越盲信。

可用的指標

指標怎麼量代表什麼
一次通過率無需修正就被接受的任務比例指令與規範的品質
返工次數每個任務被要求修改的次數理解與執行的落差
審查發現率交叉審查抓到的已證實問題數實作品質與審查有效性
缺陷逃逸上線後才發現、本該在審查抓到的問題防線漏洞
範圍偏離改動了不該動的檔案的次數約束是否清楚
驗證通過率驗證報告中「不通過」的比例是否有誠實驗證
耗時與成本完成任務的時間與用量效率

建立小型評測集

挑 5～10 個代表性任務，附上「期望結果」與「怎麼判斷通過」，每次調整設定後重跑一遍。

任務期望判定
修一個已知 bug（附重現步驟）找到根因並補回歸測試測試先失敗後通過
新增欄位驗證沿用既有驗證模式diff 只含相關檔案、測試通過
解釋一段複雜程式說明正確、不編造由熟悉的人對照
審查含已知缺陷的 PR抓到植入的 2 個缺陷命中數

比較改動前後

  • 一次只改一個變數（模型、CLAUDE.md、skill、提示），其他不動。
  • 同一組任務各跑數次（結果有隨機性，單次不具代表性）。
  • 看通過率與成本的變化，而不是挑單一漂亮案例。

抽樣審查

  • 即使信任度提高，也定期隨機抽查 agent 的產出。
  • 特別抽查「它說完成」的項目，看證據是否真實。
  • 留意技能萎縮：自己是否還有能力看懂並判斷它的產出。

失敗要轉成改進

錯誤類型改進方向
反覆犯同一類錯補進 CLAUDE.md 或 skill 的檢查表
需求理解錯加強訪談與規格審查
驗證不實要求貼出實際輸出，加上驗證 hook 或腳本
範圍膨脹指令寫明範圍，審 diff 檔案清單
某類任務一直做不好改由人做，或拆得更小

省 Token 技巧

  • 評測集要小而精：5～10 個代表性任務即可，不必跑全套。
  • 用較小模型做例行評分的前置整理，最終判斷仍由人或高風險時的大模型。
  • 把量測自動化：測試通過與否由腳本判斷，不要靠 agent 自評。
