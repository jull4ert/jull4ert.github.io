食譜：寫 xUnit 測試

讓 agent 寫「真的有保護力」的測試，而不是為了覆蓋率而寫的空殼。

什麼是好測試

特徵說明
測一件事一個測試一個情境，名稱說明「情境＿預期」
有實際斷言斷言具體的值，而不是「不為 null」
會失敗實作改壞時它會失敗（用臨時破壞驗證）
獨立、可重複不依賴順序、時間、外部服務

步驟

  1. 請 agent 先列出要測的行為與邊界（表格），你挑選。
  2. 指定風格：Arrange / Act / Assert、命名規則、參考的既有測試檔。
  3. 先確認測試會失敗（新行為）或會通過（記錄現況）。
  4. 用臨時破壞確認測試有保護力。

提示範例

> 為 OrderService.List 補 xUnit 測試。
> 風格請參考 @tests/OrderDemo.Tests/OrderServiceTests.cs（命名、AAA、使用 InMemoryOrderRepository）。
> 涵蓋：不存在的部門、狀態沒有符合的資料、日期區間邊界（含頭尾兩天）。
> 不要使用 Moq，也不要修改正式程式碼。執行 dotnet test --filter "FullyQualifiedName~OrderServiceTests" 並貼出結果。

常用語法

[Fact]                                  // 單一情境
[Theory]                                // 同一邏輯、多組資料
[InlineData(OrderStatus.Draft)]
[InlineData(OrderStatus.Submitted)]
public void Cancel_AllowedStatuses_Succeeds(OrderStatus status) { ... }

Assert.Equal(expected, actual);
Assert.Throws<InvalidOperationException>(() => service.Do());
Assert.All(collection, item => Assert.Equal(1, item.DepartmentId));

只跑部分測試

dotnet test --filter "FullyQualifiedName~Cancel"     # 名稱包含 Cancel
dotnet test --filter "FullyQualifiedName~OrderServiceTests.Cancel_ShippedOrder_Fails"

常見的壞測試（要叫 agent 修）

壞味道改善
沒有斷言，或只斷言 Assert.NotNull斷言具體行為
過度 mock，測的是 mock 本身能用簡單的假實作（如記憶體 Repository）就不用 mock 框架
一個測試驗太多事情拆開
依賴目前時間、隨機、檔案系統注入時間或固定值
測試之間共享可變狀態每個測試建立自己的資料
為了通過而複製正式程式的邏輯來算期望值期望值用寫死的、你能獨立判斷的值

驗證測試有效：臨時破壞

  1. 手動改壞一行正式程式（例如把條件取反）。
  2. 執行測試，應有測試失敗。
  3. git restore 還原。

也可以請 agent 做：「請對 Cancel 方法依序做 3 個小的破壞性修改（每次只改一處），每次執行相關測試並回報是否有測試失敗，最後還原所有修改。」

檢查清單

  • 每個測試名稱能獨立說明情境與預期。
  • 斷言具體。
  • 臨時破壞時測試會失敗。
  • 沒有為了通過而改正式程式或既有測試。
