食譜：安全重構

先鎖住行為，再小步整理；重構不該改變功能。

情境

一個 Controller 動作有 200 行，邏輯、驗證、資料存取全混在一起。你想把它拆乾淨，但不想弄壞功能。

核心規則

  1. 沒有測試就不重構：先補特徵測試鎖住現況（見 Lab 3、範例 B）。
  2. 一次一種重構：抽出方法、搬移到 Service、改名，不要同時做。
  3. 小步提交：每步測試全綠就 commit，壞了可以精準退回。
  4. 不改行為：重構的 diff 不該包含新功能或 bug 修正。

步驟

  1. 唯讀分析：「列出這個動作做了哪些事（驗證、授權、查詢、計算、組回應），並建議如何分層，先不要改。」
  2. 補特徵測試，確認全綠。
  3. 請它列出重構步驟清單（每步獨立可驗證），你審核。
  4. 每一步新對話或明確指示： 
    > 只做步驟 2：把訂單金額計算抽成 OrderService 的方法 CalculateTotal，
> 行為完全不變，不要改名、不要整理其他程式。
> 完成後執行全部測試並貼出結果。
  5. 每步後看 git diff，確認只是搬移與抽取。

典型重構目標（MVC）

壞味道方向
Controller 內有商業邏輯抽到 Service
Controller 直接操作 DbContext／Repository透過 Service 與介面
View 裡有複雜的 C# 邏輯移到 ViewModel 或 Service
重複的程式碼抽出共用方法（先確認「真的是同一件事」）
過長的方法、深巢狀提早 return、拆小方法
魔術數字與字串常數或列舉

讓 agent 守規矩

  • 明確說：「不要順便修 bug、不要改公開方法的簽章、不要新增套件。」
  • 發現疑似 bug 時：「列出來給我，不要修。」
  • 要求每步貼出測試結果。

陷阱

陷阱對策
agent 一次改幾十個檔案限定步驟與範圍；用 --stat 檢查
測試為了配合重構被修改規定不得修改既有測試（除非介面確實改了，且要說明）
重構中悄悄改變行為特徵測試、人工審 diff
為了「更乾淨」而過度設計要求維持簡單，符合專案現有慣例
