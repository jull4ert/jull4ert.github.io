食譜：資料存取、EF 與 SQL

資料庫是不可逆風險最高的地方：讓 agent 輔助，但關鍵決定留給人。

先講原則

可以交給 agent必須由你（或資深同事）決定
解釋既有的查詢與 LINQ資料表結構變更
寫查詢草稿、提出索引建議產生與套用 migration
在測試資料庫或記憶體資料上驗證對正式資料庫執行任何寫入、刪除、結構變更
審查產生的 SQL 與效能風險大量資料更新、資料修補腳本的執行
Migration 一律人工決定。agent 可以說明「這次的模型變更需要一份 migration、內容大致是什麼」，但不要讓它自行執行新增、修改或套用 migration 的指令。建議把這條寫進 CLAUDE.md 並在權限設定中禁止。

環境與權限

  • 開發用本機或測試資料庫，不要連正式資料庫。
  • 連線帳號用唯讀或最小權限，連線字串放在祕密管理或環境變數，不要寫進被版控的檔案。
  • 不要把正式資料（個資、交易）貼進對話；需要樣本時用去識別化資料。

步驟：讓 agent 輔助寫查詢

  1. 提供結構而不是資料：資料表、欄位、關聯、索引（可從模型類別或 schema 取得）。
  2. 說明需求與資料量級：「約 100 萬筆、依建立日期與狀態查詢」。
  3. 要求同時說明索引需求與風險。
  4. 在測試環境驗證結果正確，並看實際執行計畫。
> 這是 Order 的模型與目前的 EF 設定（@檔案）。
> 需求：依部門、狀態、建立日期區間查詢，並分頁，資料量約 100 萬筆。
> 請寫出 LINQ 查詢，並說明：產生的 SQL 大致長什麼樣、需要什麼索引、
> 有沒有 N+1 或載入過多欄位的風險。不要建立 migration，也不要修改任何設定。

EF Core 常見的審查點

問題提問方向
N+1 查詢「迴圈中有沒有再查資料庫？該用 Include 或投影嗎？」
載入過多「是否只需要部分欄位？能用投影（Select）嗎？」
只讀查詢的追蹤成本「唯讀的查詢是否該用 AsNoTracking？」
在記憶體中過濾「這個條件是在資料庫執行，還是先把全部載入再用 LINQ to Objects 過濾？」
交易與併發「兩個請求同時修改同一筆資料會怎樣？需要交易或樂觀並行控制嗎？」
字串拼接 SQL「是否有把使用者輸入拼進 SQL？一律用參數化。」

資料修補腳本

要修正正式資料時（例如補欄位、更正資料）：

  1. agent 只協助撰寫與審查腳本，不執行。
  2. 腳本要先 SELECT 確認影響筆數與內容，再 UPDATE。
  3. 在測試環境用複製的資料演練。
  4. 備份、在交易中執行、有回復方案。
  5. 由有權限的人執行，並有紀錄。

檢查清單

  • 沒有連到正式資料庫，沒有貼出個資。
  • 沒有自動執行任何 migration 或結構變更。
  • 查詢已在測試資料上驗證結果正確。
  • 已檢查索引、N+1、載入量。
  • SQL 都是參數化，沒有字串拼接。
