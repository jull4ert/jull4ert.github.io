食譜：新增一支 API（含前端串接）

從規格到 Controller、Service、測試、Vue 呼叫，一支 API 該有的樣子。

情境

要新增「依訂單編號查詢單一訂單」的 API，並在前端顯示詳情。

步驟

  1. 先定義契約（寫成規格的一小段）：路由、方法、參數、成功回應、錯誤回應、授權規則。 
    GET /api/orders/{id}
- 成功 200：{ id, customerName, status, total, createdAt, shippedAt }
- 找不到或不屬於呼叫者部門：404（不洩漏是否存在）
- 未登入：401
  2. Service 先行：先寫測試（找得到、找不到、他部門），再實作。
  3. Controller 薄：只做參數、呼叫 Service、回對應的狀態碼。
  4. 授權：部門從登入身分取得，不信任請求參數。
  5. 前端串接：呼叫 API、處理 200 / 404 / 其他錯誤，並顯示對使用者有意義的訊息。
  6. 驗證：用 curl 或瀏覽器實測，確認各狀態碼。

提示範例

> 依 @docs/specs/order-detail.md 新增 GET /api/orders/{id}。
> 慣例請參考 @src/OrderDemo.Web/Controllers/Api/OrdersApiController.cs，
> 商業邏輯放 OrderService，Controller 只做轉接。
> 先在 OrderServiceTests 寫會失敗的測試（找得到、找不到、他部門），再實作。
> 授權規則：不要從查詢字串信任 departmentId；先告訴我你打算怎麼取得目前使用者的部門，等我確認。

最後一句很重要：授權相關的設計，要讓 agent 先講、你確認，不要讓它自行決定。

一支 API 的檢查表

面向檢查
輸入驗證型別、範圍、必填；不合法回 400，並有清楚訊息
授權誰能呼叫？只能看自己部門嗎？不是靠前端隱藏按鈕
錯誤碼400 / 401 / 403 / 404 / 409 / 500 用得合理，且不洩漏內部細節
回應格式與既有 API 一致（大小寫、列舉、日期格式）
測試Service 單元測試；必要時 API 整合測試
效能沒有明顯的 N+1、回傳過多欄位
文件規格或 API 說明已更新

.NET 小提醒

  • [ApiController] 會自動做模型驗證並回 400，但你仍要驗證業務規則。
  • 回傳實體（Entity）給前端容易洩漏欄位，建議用專用的回應類型（DTO）。
  • 列舉要不要序列化成字串（本專案設定為字串），前後端要一致。

陷阱

  • agent 為了方便，把 departmentId 當參數（練習專案現況就是這樣，是已知缺陷）。
  • 只回 200 或 500，沒有區分情況。
  • 前端沒處理失敗情況。
