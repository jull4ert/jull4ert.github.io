Lab 6：交叉審查：找出隱藏的缺陷

拿一份含缺陷的變更，用多個 agent 交叉審查，並對發現做出裁決。

預計時間：60～90 分鐘　素材：docs/labs/review-me.diff

情境

同事送出一個 PR：新增「依部門統計平均金額與取消率」的 API。變更內容放在 docs/labs/review-me.diff（這是一份檔案，沒有套用到專案）。請你做審查。

目標

  • 練習第 05 章的方法：獨立 subagent、多視角、對抗式驗證、證據、裁決。
  • 先自己審一遍，再讓 agent 審，比較誰找到什麼。

步驟

  1. 先自己看 10 分鐘，把你覺得有問題的地方寫下來（不查任何東西）。
  2. 建立或使用唯讀的審查 subagent（見 05 程式碼審查、模板庫）。
  3. 多視角平行審查： 
    > 請同時啟動 3 個 subagent，各自獨立審查 @docs/labs/review-me.diff，
> 視角分別是：正確性、安全與授權、可維護性與測試。
> 每個發現都要有：嚴重度、位置、問題、證據或推論、信心程度。
> 沒有高嚴重度問題請直說，不要湊數。不要修改任何檔案。
  4. 對高、中嚴重度發現做對抗式驗證：請另一個 agent 嘗試反駁並提出證據。
  5. 挑一個你認為成立的發現，請 agent 寫會失敗的測試或重現步驟（把 diff 的檔案暫時加到練習專案的分支中）。
  6. 整理成裁決表：發現、狀態（已證實／可能／推測）、嚴重度、決定（採納／延後／駁回）、理由。

預期結果

一份裁決表；你自己找到的與 agent 找到的對照；至少一個以測試或重現證實的缺陷。

檢核

  • 審查者彼此獨立，沒有看到我的結論。
  • 每個採納的發現都有證據。
  • 我駁回了至少一項（並寫下理由）。
  • 我能說明為什麼不能只靠一個 agent 審自己。
預先埋設的缺陷（做完再打開）
#缺陷類型
1departmentId 由呼叫端傳入，沒有驗證呼叫者是否屬於該部門，任何人都能看任何部門的統計授權／安全（高）
2部門沒有訂單時：orders.Sum(...) / orders.Count 除以零，First() 也會對空集合丟例外正確性（高）
3catch (Exception) 把所有例外吞掉並回傳 { count = 0 }，讓缺陷 2 變成「看起來正常但資料是錯的」錯誤處理（高）
4cancelled * 100 / orders.Count 是整數除法，取消率會被無條件捨去正確性（中）
5Controller 直接使用 IOrderRepository，繞過 Service，違反專案分層慣例可維護性（中）
6沒有任何測試測試（中）
7最高金額客戶只取第一筆，並列時結果不確定；回傳的欄位未文件化低

缺陷 2 與 3 的交互作用最值得討論：單看任一項，都像「有處理」；合在一起才是真正的問題。這正是交叉審查與證據導向的價值。
