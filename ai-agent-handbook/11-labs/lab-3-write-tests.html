Lab 3：補測試與驗證測試有效

為現有行為補上測試，並用「臨時破壞」確認測試真的有保護力。

預計時間：60 分鐘　分支：lab3-tests

目標

  • 為邊界與錯誤情境補測試（特徵測試：記錄現況）。
  • 學會判斷「這個測試有沒有用」。
  • 前端純函式也補測試。

步驟

  1. 請 agent 列出尚未被測試涵蓋的行為，先不要寫： 
    > 閱讀 OrderService 與 tests/OrderDemo.Tests/OrderServiceTests.cs，
> 列出尚未被測試涵蓋的行為與邊界情境（表格：情境、預期結果）。
> 先只列清單，不要寫程式。
  2. 你挑 3～4 個，並自己先預測「現在的程式會怎樣」。
  3. 請它撰寫測試： 
    > 為上述選定的情境新增 xUnit 測試，遵守既有的命名與 Arrange/Act/Assert 風格。
> 期望值依「現有程式的實際行為」，不要修改正式程式碼。執行並貼出結果。
  4. 臨時破壞驗證：手動改壞一行正式程式（例如把 DepartmentId == 改成 !=），執行測試，應該要有測試失敗。沒有就代表測試沒保護力。完成後用 git restore 還原。
  5. 前端：為 order-utils.js 補測試，包含 formatDate(null) 的現況。

預期結果

  • 新增 3～4 個通過的後端測試與 1～2 個前端測試。
  • 臨時破壞時，至少一個測試失敗。
  • 發現 formatDate(null) 會丟出例外（現況）。

檢核

  • 每個測試都有清楚的名稱與實際的斷言（不是只斷言不為 null）。
  • 我做過「臨時破壞」驗證，且已還原。
  • 我知道特徵測試記錄的是「現況」，不代表「正確」。
參考解答

後端（以下情境都是現況行為，已對照程式確認）：

[Fact]
public void List_UnknownDepartment_ReturnsEmpty()
{
    var orders = CreateService().List(departmentId: 99);

    Assert.Empty(orders);
}

[Fact]
public void List_StatusWithNoMatch_ReturnsEmpty()
{
    var orders = CreateService().List(departmentId: 2, status: OrderStatus.Cancelled);

    Assert.Empty(orders);
}

[Fact]
public void Cancel_NonExistentOrder_Fails()
{
    var result = CreateService().Cancel(orderId: 999, departmentId: 1);

    Assert.False(result.Success);
    Assert.Equal("找不到訂單", result.Error);
}

前端（現況：傳入 null 會丟出 TypeError）：

  assert.throws(() => formatDate(null), TypeError);

想一想

第一個「formatDate 遇到 null 會丟例外」的測試，在 Lab 5 修好 formatDate 之後會失敗。這時該改測試還是改程式？（答案：行為是你有意改變的，所以更新測試；但要在 PR 說明中講清楚這是有意的行為變更。）
