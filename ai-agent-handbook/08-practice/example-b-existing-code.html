範例 B：既有專案加功能並補測試

在沒有測試、結構雜亂的舊程式上動手：先保護，再修改。

這是示意情境。對話、檔名、數字都是為了說明流程而設計的範例，不是真實專案的執行結果；請把它當成可改造的腳本，換成你自己的專案與資料。

情境

一個運作多年的出貨計算模組，沒有測試，邏輯散在好幾個方法裡。要新增「某類客戶免運費」的規則。直接改很危險：沒人確定現有行為完整是什麼。

策略：先鎖住現況，再改

① 理解現況（唯讀） → ② 補「特徵測試」鎖住現有行為 → ③ 才加新規則（先寫新規則的失敗測試） → ④ 全部測試通過 + 交叉審查 → ⑤ 交付

時間軸

#階段做法
1理解現況計畫模式、唯讀：「說明運費計算的流程、分支與已知特殊情況，列出相關檔案，不要貼大段程式碼」；用 subagent 探索並只回報摘要
2記錄理解把摘要存成 docs/notes/shipping-current-behavior.md，之後直接讀，不重新探索
3補特徵測試「針對現有行為寫測試，輸入與期望值取自目前實際輸出；不要修改任何正式程式碼」。這是記錄現況，不是判斷對錯
4確認測試有效臨時改動一行計算邏輯，看測試是否會失敗（驗證測試真的在測）
5寫新規則的測試依需求寫「免運費客戶」的測試，先確認失敗
6實作最小的修改讓新測試通過，且特徵測試全數維持通過
7審查獨立 subagent：「這份 diff 有沒有改變既有行為？」，並反駁
8交付PR 說明列出：保護了哪些行為、新增了什麼、沒動什麼

範例提示：特徵測試

> 針對 @src/Shipping/ShippingCalculator.cs 目前的行為補測試。
> 規則：
> - 不修改正式程式碼
> - 每個測試的期望值，是呼叫現有程式後得到的實際結果
> - 涵蓋：不同重量區間、不同地區、空購物車、超重
> - 發現疑似 bug 的行為，仍照現況寫測試，並在測試名稱加「（疑似錯誤）」，另列清單給我
> 完成後執行測試並貼出結果。

「疑似 bug 也照現況鎖住」的好處：你有意識地決定要不要順便修，而不是在加功能時不小心改變行為。

你做的決定

  • 疑似錯誤的行為：保留、還是另開任務修？
  • 新規則與既有規則衝突時，以哪個為準。

可能出錯的地方

坑對策
agent 順手重構明確規定「不要整理、不要改名，只做這件事」
為了讓測試通過而改測試規定不得修改特徵測試
特徵測試寫成必過用「臨時破壞」驗證測試會失敗
探索結果太籠統要求列出分支條件與實際例子

檢查清單

  • 改動前後，特徵測試都全數通過。
  • 新規則有獨立的測試。
  • diff 只含必要檔案。
  • 疑似錯誤清單已交給負責人決策。
  • 現況說明文件已存檔，供下次使用。

省 Token 技巧

  • 探索結果存成短文件，下次直接讀。
  • 探索與審查用 subagent，只回報結論。
  • 一個任務一個對話；特徵測試與新功能分開做。
  • 大型舊檔案只讀相關方法，用 @ 引用指定檔案。
