範例 A：一句話需求到交叉審查

從「訂單列表加篩選」這一句話，走完訪談、規格、拆解、實作、驗證、審查、交付。

這是示意情境。對話、檔名、數字都是為了說明流程而設計的範例，不是真實專案的執行結果；請把它當成可改造的腳本，換成你自己的專案與資料。

情境

客服主管說：「訂單列表要能依狀態和日期篩選。」團隊使用 .NET 後端加網頁前端，專案已有 CLAUDE.md 與測試。

對話片段：訪談

你　　：（計畫模式）要做訂單列表篩選，給客服用。先訪談我。
Agent：日期指建立日期還是出貨日期？建議：兩者都支援，可同時選。
你　　：同意。
Agent：兩個條件同時選是 AND 還是 OR？建議：AND。
你　　：AND。
Agent：程式碼中列表已依 DepartmentId 過濾。這次要沿用嗎？
你　　：沿用，不新增例外。
Agent：目前沒有重大不確定處。仍未決：是否記住上次條件？
你　　：先列未決，這次不做。

對話片段：反駁一項審查發現

審查者：OrderService.Cancel 對已出貨訂單仍可取消。（嚴重度：高）
反駁者：讀程式碼後，Cancel 在狀態檢查前已回傳。請先寫測試重現。
Agent ：測試通過（代表問題不成立），原因：Controller 層已先攔截。測試已刪除。
你　　：駁回，記錄理由。

你做的決定（agent 不能代替）

  • 訪談中的取捨：AND 或 OR、哪些不做。
  • 審查後哪些發現採納、哪些駁回。
  • 最後是否合併。

可能出錯的地方

坑對策
訪談結束仍有隱含假設要求「凡是假設都明說」，並用事前驗屍再檢一次
實作時順手改了其他模組「只做任務 N」，看 git diff --stat
測試通過但沒實際跑起來驗證階段要求啟動並走流程、貼證據
審查意見太多太雜要求證據與嚴重度，只反駁高中嚴重度

檢查清單

  • 決策紀錄、規格、計畫檔都已存檔並入版控。
  • 每個驗收條件都有對應證據。
  • 審查發現都有裁決與理由。
  • PR 說明含驗證與審查紀錄。
  • 學到的事已回寫到 CLAUDE.md、ADR 或術語表。

省 Token 技巧

  • 每個階段結束 /clear，下一階段只讀上一階段的檔案。
  • 探索與審查交給唯讀 subagent，限制回報長度。
  • 實作只跑相關測試，驗證階段才跑全套。
  • 審查只針對 diff，並依風險決定視角數。
