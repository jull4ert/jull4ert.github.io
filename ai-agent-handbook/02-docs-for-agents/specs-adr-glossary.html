讓 agent 懂「為什麼」和「這個詞是什麼意思」。

三種最有價值的專案文件

文件回答的問題agent 用它做什麼
規格 / PRD要做什麼、做到什麼算完成對照需求實作、產生測試、審查是否偏離
ADR（架構決策紀錄）為什麼選 A 不選 B避免推翻既有決定、理解限制
GLOSSARY（術語表）領域詞彙的精確定義命名一致、少誤解需求

規格怎麼寫（agent 友善版）

  • 目標與非目標（明寫「不做什麼」）。
  • 使用情境，每個附可驗證的驗收條件（Given / When / Then 或條列）。
  • 邊界與錯誤情境：空值、權限不足、重複送出、併發。
  • 未決問題清單（讓 agent 知道哪些不能自行假設）。

ADR 範本

# ADR-007 查詢統一使用 Query 物件
狀態：已採用（2026-03）
背景：Controller 直接寫 LINQ，導致分頁與權限邏輯分散。
決定：所有查詢封裝為 Query 物件，集中處理分頁與權限。
後果：新增查詢需多一個類別；換得一致性與可測試性。
被否決方案：Repository 回傳 IQueryable（難以控制效能）。

術語表範例

- 訂單（Order）：客戶已送出且未取消的購買紀錄；草稿不算。
- 出貨單（Shipment）：一張訂單可拆成多張出貨單。
- 避免用語：「單」（有歧義，請用上列正式名詞）。

放哪、怎麼讓它讀到

  • 放在 docs/（規格、ADR）與根目錄 GLOSSARY.md。
  • CLAUDE.md 只放索引與一句話說明：「領域用語見 @GLOSSARY.md；決策見 docs/adr/」。
  • 任務開始時明確指示：「先讀 @docs/specs/order-filter.md」。

省 Token 技巧

  • 規格寫成可分段讀取：標題清楚、每節獨立，讓 agent 只讀與任務相關的章節。
  • 任務指令引用章節，不引用整份：「依規格 §3 情境 2 實作」。
  • 術語表保持精簡：只收有歧義、易誤解的詞，不是字典。
  • ADR 一份一決策：短小獨立，需要時才讀特定一份。
  • 把探索成果存成文件：下次直接讀，不必再花 Token 重新理解。
