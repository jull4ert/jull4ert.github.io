給 Agent 的寫作原則

對人好讀的文件，通常對 agent 也好讀；再加幾條針對性原則。

十條原則

#原則反例 → 正例
1具體可驗證「程式要乾淨」→「單一函式不超過 40 行，巢狀不超過 3 層」
2先講結論與指令先給「怎麼跑測試」，再講背景
3附原因「不要改 Migrations」→「…因為已部署，改了會造成環境不一致」
4給範例勝過形容附一段符合規範的程式碼或「參考 @某檔案」
5說明邊界與優先序規則衝突時以何者為準
6單一事實來源同一規則只寫一處，其他地方連結
7結構化標題、條列、表格，利於定位
8常駐要短，細節按需主檔放索引，細節放獨立檔案或 skill
9維持新鮮過時文件比沒有文件更糟，隨變更一起改
10用行為驗證寫完讓 agent 執行任務，看是否照做；不照做就改文件

強調語氣要節制

滿篇「絕對」「必須」「永遠」會稀釋重點。只在真正不可違反處使用，並說明理由；一般偏好用平述句即可。

文件的壞味道

  • 超長：agent 讀了但抓不到重點。
  • 互相矛盾：兩份文件對同一件事說法不同。
  • 抽象口號：「寫高品質程式」無法執行也無法檢查。
  • 混入暫時資訊：進度、待辦、除錯筆記放進常駐檔。

快速自檢

  • 新同事（或 agent）只讀這份，能不能跑起專案、跑通測試？
  • 每條規則是否能被檢查、有無原因？
  • 有沒有重複或矛盾的規則？
  • 上次 agent 犯的錯，有沒有對應規則？

省 Token 技巧

寫法為什麼省
先講結論與指令agent 讀到答案就能停，不必讀完整篇背景
具體可驗證的規則少一輪「我理解對嗎」的來回
單一事實來源不會同一件事在多處重複載入
表格與條列取代長段落相同資訊量，字數更少、更好檢索
去掉客套與重複強調直接減少常駐字數

經驗：每寫一句問自己「刪掉這句，agent 會做錯嗎？」不會，就刪。
