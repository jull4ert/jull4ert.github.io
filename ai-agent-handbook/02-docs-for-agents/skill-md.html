SKILL.md：按需載入的專業流程

把「某類任務怎麼做」封裝成 agent 在需要時才讀的文件。

與 CLAUDE.md 的差別

CLAUDE.mdSKILL.md
載入時機每次對話都載入只常駐名稱與描述；判斷相關才載入全文
適合常駐規範特定任務的流程、檢查表、專業做法
觸發無需觸發靠 description 比對任務；也可手動呼叫

這是「漸進式揭露」：目錄常駐、細節按需讀，讓你能裝很多 skill 而不撐爆情境。

結構

.claude/skills/
└─ code-review-checklist/
   ├─ SKILL.md          ← 必要：前言 + 說明
   ├─ checklist.md      ← 選用：被 SKILL.md 引用的參考資料
   └─ scripts/lint.sh   ← 選用：可執行的腳本

個人層級放 ~/.claude/skills/，專案層級放 .claude/skills/（可入版控與團隊共用）。

範例

---
name: code-review-checklist
description: 審查 C# 變更時使用。當使用者要求 review、檢查 diff 或 PR 時套用，涵蓋授權、錯誤處理、效能與測試。
---
# 審查流程
1. 先讀 git diff，列出變更範圍。
2. 依 [checklist.md](checklist.md) 逐項檢查。
3. 輸出：嚴重度排序的問題清單，每項附檔案行號與建議。
4. 不要自行修改程式碼，只回報。

寫好 description 是關鍵

  • 說明「做什麼」以及「何時使用」，並包含使用者會說的關鍵詞。
  • 邊界要清楚：什麼情況不要用，避免誤觸發。
  • 太籠統（「幫忙寫程式」）會亂觸發；太窄會永遠不觸發。

撰寫原則

  • 主檔保持精簡（建議數百行內），細節拆到旁邊的檔案，由主檔指向。
  • 把流程寫成步驟與輸出格式，而非散文。
  • 需要穩定結果的部分（格式檢查、轉換）放成腳本，不要靠 agent 即興。
  • 用真實任務測試：觸發了嗎？照做了嗎？哪裡跑偏就改哪裡。
  • 一個 skill 一件事；彼此可組合，不要做萬用大雜燴。

什麼該做成 skill

你發現自己對 agent 重複貼同一段指令時：commit 慣例、PR 說明格式、審查清單、報表產生流程、公司術語翻譯。

省 Token 技巧

  • Skill 本身就是省 Token 設計：只有名稱與描述常駐，全文在需要時才載入（漸進式揭露）。
  • description 要精簡：它是常駐成本，用一兩句講清楚做什麼與何時用，不要寫成長文。
  • 主檔精簡、細節外放：把大型參考資料拆到旁邊的檔案，主檔只指向，用到才讀。
  • 穩定的邏輯放腳本：腳本執行不佔推理成本，輸出也可控；只讓 agent 讀結果。
  • 不用的 skill 就移除：每個都有常駐描述的成本。
  • 把重複貼的長指令搬進 skill：從「每次貼」變成「按需載入」。
