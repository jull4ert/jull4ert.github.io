提示詞庫

可直接複製、改幾個字就能用的提示，依任務分類。

把 … 與括號中的內容換成你的實際情況。每個提示都內建了「範圍、限制、驗收」。

探索與理解

導覽專案

> 我是新人。請用 5 句話說明這個專案的架構，列出請求從頁面到資料的路徑（附檔案路徑），
> 以及最值得先讀的三個檔案。先不要修改任何檔案。

解釋一段程式

> 請逐段解釋 @檔案路徑 的 方法名。每段一句話；列出前提假設與最可能出錯的三個地方。
> 用初學者能懂的方式，不要貼大段程式碼。

找出所有用到某物的地方

> 列出所有讀取或寫入「Order.Status」的地方（檔案與方法），分成讀取與寫入兩組，
> 不要貼程式碼，我要評估修改它的影響範圍。

需求與規格

訪談

> （計畫模式）我想做：…。先不要寫規格或程式。請訪談我：一次只問一個問題、
> 每題附建議答案與理由、能從程式碼查到的別問我，問到沒有重大不確定處為止。

寫規格

> 依 @決策紀錄檔 撰寫規格 docs/specs/….md：目標、非目標、情境與驗收條件（Given/When/Then）、
> 邊界與錯誤、影響範圍、未決問題。只用決策紀錄中的內容，不確定的寫進未決問題。

事前驗屍

> 假設這個功能上線一個月後被判定失敗。請讀 @規格檔，列出最可能的 7 個原因，依可能性排序，
> 每項說明觸發條件、影響，以及規格中缺了什麼。只做分析，不要修改檔案。

實作

先寫失敗的測試

> 依 @規格檔 的驗收條件 N，在 @測試檔 新增 xUnit 測試（風格參考該檔案既有測試）。
> 只加測試，不修改正式程式碼。執行 dotnet test --filter … 並貼出結果，我要看到它失敗。

實作任務

> 執行 @計畫檔 的任務 N。規格見 @規格檔。先寫失敗的測試，再實作；只做任務 N；
> 寫法參考 @範例檔。完成後貼出測試輸出與改動檔案清單。

除錯

> 重現步驟：…　預期：…　實際：…　例外：（貼最前面 20 行）
> 請閱讀相關程式，列出 3 個最可能的根因，每個說明為什麼，以及我怎麼驗證。現在不要修改檔案。

測試與驗證

找測試缺口

> 閱讀 @類別 與 @測試檔，列出尚未被測試涵蓋的行為與邊界（表格：情境、預期）。先只列清單。

臨時破壞驗證

> 針對 方法名，依序做 3 個小的破壞性修改（每次只改一處），每次執行相關測試並回報是否有測試失敗，
> 最後還原所有修改並確認 git diff 為空。

產出證據表

> 所有任務已完成。請做完整驗證：建置、lint、全部測試；啟動並走過規格的每個情境；
> 產出表格「驗收條件｜驗證方式｜證據｜結果」。任何不通過或無法驗證的項目請明說，不要自行判定通過。

審查

獨立審查（subagent）

> 用 code-reviewer 審查目前未提交的變更，規格見 @規格檔。
> 每個發現附：嚴重度、檔案與行號、問題、證據、信心。沒有高嚴重度請直說。不要修改檔案。

反駁

> 以下是審查者提出的發現（貼上）。請逐項讀實際程式碼嘗試反駁，回答：成立／不成立／無法判斷，
> 並附證據。你不是在幫作者辯護，而是在剔除誤報。

彙整成裁決表

> 彙整以下審查輸出：合併重複項並註明幾位提出、標示狀態（已證實／可能／推測）、
> 依影響乘機率排序並估修復成本、矛盾意見單獨列出。不要替我做決定。

重構

> 只做這一步：把 … 抽成 …，行為完全不變，不要改名、不要整理其他程式、不要順便修 bug。
> 完成後執行全部測試並貼出結果；疑似 bug 請列給我，不要修。

學習

> 我的理解是：「…」。請指出我理解錯誤或遺漏的地方，並給一個會讓我的理解出錯的具體例子。
> 我想自己做這個。請不要直接給答案，用提問引導我。

交付

> 依目前的 git diff 寫 commit message：第一行 50 字內，空一行，說明為什麼改與影響。
> 只寫 diff 中確實存在的內容。
> 依這個分支的變更寫 PR 說明：背景、變更、如何驗證（附測試結果）、風險與回滾、審查紀錄。
> 只寫有證據的內容。

寫好提示的四句話

  • 範圍：「只改…，不要動…」
  • 限制：「沿用…的寫法，不新增套件」
  • 驗收：「新增測試並通過，貼出輸出」
  • 節奏：「先給計畫，我確認後再改」
