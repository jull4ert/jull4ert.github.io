寫出好指令

好指令 = 目標 + 範圍 + 限制 + 驗收方式。

四要素

要素說明範例
目標要的結果，不是步驟「訂單列表可依狀態篩選」
範圍該動與不該動的地方「只改 Orders 模組，不動資料庫結構」
限制風格、相容性、禁忌「沿用現有 Repository 寫法，不新增套件」
驗收怎麼證明完成「新增單元測試並全數通過；貼出測試輸出」

對照

模糊具體
幫我加篩選功能在訂單列表加「狀態」下拉篩選，沿用 OrderQuery 的條件模式；先給計畫，我確認後再改；完成後跑相關測試並貼結果
這個有 bug，修一下重現步驟：…；預期：…；實際：…；錯誤訊息：…。先找根因並說明，再修，補一個會失敗的回歸測試

幾個高報酬習慣

  • 先問再做：「做之前，有哪些不清楚的地方請先問我」，把誤解消滅在寫碼前（見 04）。
  • 要它先講計畫：計畫比程式碼好審，改方向成本低。
  • 給範例：「寫法請參考 @Services/FooService」，勝過口頭描述風格。
  • 要證據：要求貼出執行結果，不接受「應該可以」。
  • 一次一件事：大任務拆成可獨立驗收的小段。
  • 事後學習：它做錯時，問「為什麼這樣做」，再把原因對應的規則寫進 CLAUDE.md。
重複交代超過兩次的話，就不該再用嘴說，改寫進文件（見 02）。

省 Token 技巧

  • 具體的指令 = 少走冤枉路：指明檔案或資料夾，省下它大範圍搜尋、讀一堆無關檔案的成本。
  • 一次一件事：混在一起的任務會讓情境塞滿，之後每一輪都更貴。
  • 先要計畫：計畫只是幾百字，比寫完上千行程式碼再被推翻便宜得多。
  • 限制輸出：告訴它要什麼格式與長度，例如「只列問題清單，每項一行」「不用複述程式碼」。
  • 給驗收方式：它有明確的終點，就不會一直自行加碼或反覆微調。
  • 修正要精準：「第 3 個方法的邊界判斷錯了」勝過「這邊有問題，再看看」。
