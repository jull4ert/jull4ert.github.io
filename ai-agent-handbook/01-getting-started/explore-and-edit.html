讀懂專案與小修改

最安全的起手式：先唯讀探索，再做可退回的小改動。

步驟一：唯讀探索

先不要讓它改任何東西，用問題建立你對專案和 agent 理解程度的雙向認識：

  • 「用 5 句話說明這個專案的架構與資料流。」
  • 「從使用者按下『送出訂單』開始，列出經過的檔案與函式。」
  • 「測試怎麼跑？目前有哪些測試？覆蓋哪些模組？」
若它的回答和你所知不符，代表它缺脈絡或讀錯方向，這正是補 CLAUDE.md 的時機。

步驟二：計畫模式提出小修改

切到計畫模式，描述一個你本來就想做的小事（例如補一個欄位驗證）。審計畫時看三點：範圍對不對、有沒有漏掉相依處、驗證方式是什麼。

步驟三：核准、看 diff、驗證

檢查怎麼做
改了哪些檔git status / git diff --stat，有沒有範圍外檔案
改得對不對逐段看 diff，特別留意刪除與條件判斷
有沒有效跑測試；前端就實際開頁面看

步驟四：決定去留

  • 滿意：commit（可請 agent 依 diff 寫 commit message）。
  • 局部不滿意：具體指出哪一段、為什麼，要求只改那段。
  • 方向錯：用 /rewind 或 git restore 退回，修正指令後重來，不要在錯的基礎上疊補丁。

省 Token 技巧

  • 限定探索範圍：「只看 Orders 模組」比「理解整個專案」省很多；全貌留給 CLAUDE.md 的架構地圖。
  • 探索結果存檔：花力氣摸清楚的架構，請它整理成短文件，下次直接讀，不必重新探索。
  • 大範圍探索用 subagent：它在獨立情境中搜尋，只把結論帶回來，主對話保持乾淨。
  • 看 diff 用 git diff --stat 先看範圍，再決定要不要讓 agent 讀完整 diff。
