平行與多 agent 分工

用 worktree 與 subagent 同時處理多件事，並設計 agent 之間的分工模式。

兩種平行方式

方式做法適合
多個 subagent（同一對話內）主 agent 派出多個，各自獨立情境，結果回到主對話探索、審查、資料蒐集等唯讀工作
多個對話 + git worktree每個對話在各自的工作目錄與分支上動手互不相依的實作任務

git worktree：讓多個 agent 不互相踩

同一個 repo 不能同時在兩個分支上改檔案。worktree 讓同一個 repo 擁有多個獨立的工作目錄。

git worktree add ../shop-filter -b feature/order-filter
git worktree add ../shop-export -b feature/order-export

# 各開一個終端機
cd ../shop-filter  && claude    # 對話 A：做篩選
cd ../shop-export  && claude    # 對話 B：做匯出

# 完成後
git worktree remove ../shop-filter

每個 worktree 是獨立資料夾，兩個 agent 同時改檔案也不會衝突；最後各自提交 PR，由你合併。

四種分工模式

模式結構範例
管線（pipeline）A 的產出交給 B，再交給 C訪談 → 規格 → 拆解（見 04）
扇出扇入（fan-out / fan-in）同一份輸入分給多人，最後彙整多視角程式碼審查（見 05）
主從（orchestrator-worker）主 agent 拆任務，派給專職 worker，再整合大型重構：每個模組一個 worker
評審團多個獨立判斷，取共識或多數重要決策、高風險審查

範例：批次遷移

> 要把 40 個舊式 Service 改成新的 Result 回傳慣例。
> 1. 先寫遷移指南 docs/migration/result-pattern.md（含改前改後範例）
> 2. 先挑 2 個檔案示範，我確認寫法
> 3. 確認後，每 5 個檔案派一個 subagent，依指南遷移並跑對應測試
> 4. 各 subagent 只回報：改了哪些檔、測試結果、遇到的例外
> 5. 最後彙整成清單，列出需要人工處理的檔案

關鍵：先用小樣本確認做法，再放大；每個 worker 的輸入（指南）與輸出（回報格式）都明確。

什麼時候不要平行

  • 任務之間有相依，後一個需要前一個的結果。
  • 會改同一批檔案（即使用 worktree，合併時也會衝突）。
  • 你來不及審查：平行產出的速度，不應超過你審查的速度。

省 Token 技巧

  • 平行省時間，不省錢：總成本是各 agent 相加；要省錢靠縮小每個任務的情境與範圍。
  • 先小樣本驗證做法：避免 40 個檔案都做錯再重來，這是最大的浪費。
  • 限制回報格式：worker 只回報摘要與結果，不貼大段程式碼。
  • worker 用較小模型：機械性遷移不需要最大模型。
  • 每個 worker 的輸入自給自足：把指南給它，不要讓每個都自己重新探索。
旗標、指令與設定欄位會隨版本調整，請以官方文件與 claude --help 的實際輸出為準；範例腳本請先在安全的環境小規模測試。
