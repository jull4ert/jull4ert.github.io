設計與維護自己的工作流程

把「發現重複 → 抽象成流程 → 上線 → 持續改進」變成習慣。

什麼值得變成工作流程

訊號例子
同樣的指令貼第三次commit 格式、PR 說明
固定時間做的例行事晨報、週報、巡檢
跨工具搬資料會議紀錄 → Trello → 行事曆
多步驟、易漏步驟發版流程、新人設定
需要多視角交叉審查

設計的六個步驟

  1. 寫下手動流程：你現在怎麼做，每一步的輸入與輸出。
  2. 分類每一步：確定性（腳本）／需判斷（agent）／需決策（你）。
  3. 決定載體：skill、subagent、hook、腳本、排程（見 03 決策表）。
  4. 定義輸出格式與關卡：產出什麼、在哪裡暫停等你核准。
  5. 先小範圍試跑：唯讀、測試資料、少量案例。
  6. 觀察與調整：看哪裡跑偏，修 skill，再放寬範圍。

步驟分類範例：發版前檢查

步驟類型載體
跑建置與測試確定性腳本 / CI
比對規格與變更，找出遺漏需判斷subagent（見 05）
檢查 migration 有沒有破壞性變更需判斷skill + 唯讀 subagent
決定是否上線需決策你
寫發版說明需判斷skill
部署確定性、高風險腳本，由你觸發

讓流程可維護

  • 版本控制：skill、agent、腳本、hook 都放進 git，變更可追溯。
  • 留下執行紀錄：時間、輸入、輸出、結果，出問題能還原現場。
  • 狀態存檔：已處理清單、建立的 ID，讓重跑安全。
  • 失敗處理：外部服務逾時、權限過期時要停下來回報，不要默默跳過。
  • 定期檢視：每月看哪些流程不再使用、哪些輸出品質下降。
  • 文件化：用 README 說明每個流程的目的、輸入、輸出、風險與負責人。

常見的失敗模式

失敗預防
流程自動化太早，品質未驗證手動觸發穩定一段時間再排程
一個 skill 做太多事拆成可組合的小流程
寫入權限放太寬最小權限、人工核准、可還原
沒有人知道它在跑通知與紀錄；有負責人
外部服務改版導致壞掉失敗時明確報錯；定期實測
過度依賴保留手動做法的文件，人要能接手

省 Token 技巧

  • 確定性步驟全部搬進腳本：零推理成本，結果穩定。
  • agent 只處理需要判斷的部分，並限制輸入範圍與輸出格式。
  • 每個流程設定上限：輪數、逾時、頻率。
  • 定期清點：關掉沒人看的排程與流程。
  • 記錄用量：知道哪個流程最花錢，才知道優化哪裡。
旗標、指令與設定欄位會隨版本調整，請以官方文件與 claude --help 的實際輸出為準；範例腳本請先在安全的環境小規模測試。
