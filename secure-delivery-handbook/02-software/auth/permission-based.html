以權限為基礎的授權（自訂角色）

端點由程式碼定義權限，角色由客戶自訂並對應權限：角色與權限分離的做法與實作。

嚴格權限控管的系統常見需求：API 端點由開發者在程式碼中定義，但「有哪些角色」「每個角色能用哪些 API」由客戶自行設定。做法是把「角色」與「權限」分開，端點只認權限，角色與權限的對應存在資料庫。

與 授權與存取控制 的關係：該頁講原則與基本寫法（固定角色）；本頁處理角色可由客戶自訂的情境。身分如何還原見 Session 與 JWT。

核心觀念：角色與權限分開

角色（Role）權限（Permission）
誰定義客戶在後台建立、改名、勾選開發者在程式碼定義
存放位置資料庫程式碼（enum 或常數），並同步一份到資料庫
例子「業務主管」「客服」「稽核」Orders.Read、Orders.Approve、Users.Manage
變動頻率隨時，不需重新部署隨版本發佈
端點檢查什麼不檢查只檢查權限

資料模型

資料表欄位說明
RolesId、Name、IsSystem角色；系統內建角色（如 ADMIN）不可刪除
PermissionsCode權限清單，啟動時由程式碼同步
RolePermissionsRoleId、PermissionCode、DataScope（可選）角色擁有哪些權限；資料範圍可放這裡，見下方
UserRolesUserId、RoleId使用者屬於哪些角色（可多個，取權限聯集）

運作流程

  1. 請求進來，驗證流程還原使用者身分。
  2. 授權層看到端點標示的權限（如 Orders.Approve）。
  3. 查「使用者 → 角色 → 權限」（有快取）。
  4. 權限集合包含此項才放行，否則回 403。
  5. 客戶在後台改角色時，清除快取，下一個請求即生效。

設計原則

  • 預設拒絕：沒標權限的端點視為錯誤，用預設政策與自動測試防止漏標。
  • 權限粒度：以「功能＋動作」為單位，不要以 URL 或過粗的角色名稱為單位；太細會讓客戶難以設定，太粗則失去控管意義。
  • 系統角色受保護：ADMIN 自動擁有所有權限（含未來新增），不可被刪除或移除權限。
  • 權限程式碼為準：客戶不能新增權限，只能組合既有權限成為角色。
  • 資料範圍另外處理：權限決定「能不能呼叫」，資料能看到哪些（本人、部門、全部）可存在 RolePermissions 的 DataScope 欄位，再於查詢層過濾。
  • 變更要即時且可稽核：角色與權限的每次修改都記錄誰、何時、改了什麼；修改後清除快取。
  • 前端只做顯示：提供「目前使用者的權限清單」API 讓前端隱藏按鈕，但後端授權才是真正防線。
  • 提供範本角色：先給幾個預設範本讓客戶複製修改，避免從空白開始而設錯。

權限放在哪裡：兩種取捨

做法優點缺點
簽進 JWT 的 Claims不用每次查資料庫權限多時 Token 很大；修改後要等 Token 到期才生效
每次查資料庫並快取（建議）修改可即時生效，Token 小要設計快取失效機制

ASP.NET Core：權限授權的完整實作

共七個步驟。每段程式碼後面的「備註」說明該項目的作用。

步驟 1　在程式碼定義權限

public enum Permission
{
    OrdersRead,
    OrdersWrite,
    OrdersApprove,
    UsersManage,
    ReportsView
}
備註：權限清單
項目作用
Permission系統所有「可被授權的功能」清單，由開發者在程式碼定義，客戶不能新增或刪除
命名方式「資源＋動作」，例如 OrdersApprove；以功能為單位而不是 URL，因為 URL 會變、功能不會
資料庫儲存存 enum 的名稱字串而不是數字，避免日後調整順序或插入項目時對應錯位

步驟 2　用屬性標在端點上

public class HasPermissionAttribute : AuthorizeAttribute
{
    public const string Prefix = "Permission:";

    public HasPermissionAttribute(Permission permission) : base(Prefix + permission)
    {
    }
}

[HasPermission(Permission.OrdersApprove)]
[HttpPost("orders/{id}/approve")]
public IActionResult Approve(int id) => this.Ok();

app.MapPost("/orders/{id}/approve", (int id) => Results.Ok())
   .RequireAuthorization(new HasPermissionAttribute(Permission.OrdersApprove));
備註：端點宣告
項目作用
HasPermissionAttribute自訂屬性，繼承 AuthorizeAttribute，讓端點用 [HasPermission(...)] 宣告所需權限，可讀性高且編譯期就能檢查拼字
Prefix把權限包成 Policy 名稱（如 Permission:OrdersApprove），讓授權系統知道要交給哪個提供者處理
Controller 寫法標在 Controller 或 Action 上；沒標權限的端點會被預設政策擋下（見後面的設定）
Minimal API 寫法用 RequireAuthorization 傳入同一個屬性，兩種寫法共用同一套機制

步驟 3　Requirement 與動態 Policy 提供者

public class PermissionRequirement : IAuthorizationRequirement
{
    public PermissionRequirement(Permission permission) => this.Permission = permission;

    public Permission Permission { get; }
}

public class PermissionPolicyProvider : DefaultAuthorizationPolicyProvider
{
    public PermissionPolicyProvider(IOptions<AuthorizationOptions> options) : base(options)
    {
    }

    public override async Task<AuthorizationPolicy?> GetPolicyAsync(string policyName)
    {
        var prefix = HasPermissionAttribute.Prefix;
        if (policyName.StartsWith(prefix) && Enum.TryParse<Permission>(policyName[prefix.Length..], out var p))
        {
            return new AuthorizationPolicyBuilder()
                .RequireAuthenticatedUser()
                .AddRequirements(new PermissionRequirement(p))
                .Build();
        }

        return await base.GetPolicyAsync(policyName);
    }
}
備註：動態 Policy
項目作用
PermissionRequirement一個「條件」物件，只記錄這個端點需要哪一項權限，真正的判斷交給 Handler
PermissionPolicyProvider當框架拿到 Permission:xxx 這種 Policy 名稱時，動態建出對應的 Policy。好處是不必為每個權限逐一註冊 Policy
RequireAuthenticatedUser先要求已登入；未登入回 401，而不是進到權限判斷
base.GetPolicyAsync不是權限類的名稱就交回預設行為，原本的一般 Policy 不受影響

步驟 4　查詢權限與判斷（含快取）

public interface IPermissionStore
{
    Task<IReadOnlySet<Permission>> GetPermissionsAsync(string userId);
}

public class PermissionStore : IPermissionStore
{
    private static CancellationTokenSource reset = new();

    private readonly AppDbContext db;
    private readonly IMemoryCache cache;

    public PermissionStore(AppDbContext db, IMemoryCache cache)
    {
        this.db = db;
        this.cache = cache;
    }

    public static void InvalidateAll()
    {
        Interlocked.Exchange(ref reset, new CancellationTokenSource()).Cancel();
    }

    public async Task<IReadOnlySet<Permission>> GetPermissionsAsync(string userId)
    {
        return (await this.cache.GetOrCreateAsync($"perm:{userId}", async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
            entry.AddExpirationToken(new CancellationChangeToken(reset.Token));

            var codes = await (from ur in this.db.UserRoles
                               where ur.UserId == userId
                               join rp in this.db.RolePermissions on ur.RoleId equals rp.RoleId
                               select rp.PermissionCode).Distinct().ToListAsync();

            return codes.Select(c => Enum.TryParse<Permission>(c, out var p) ? (Permission?)p : null)
                        .Where(p => p.HasValue).Select(p => p!.Value).ToHashSet();
        }))!;
    }
}

public class PermissionHandler : AuthorizationHandler<PermissionRequirement>
{
    private readonly ICurrentUser user;
    private readonly IPermissionStore store;

    public PermissionHandler(ICurrentUser user, IPermissionStore store)
    {
        this.user = user;
        this.store = store;
    }

    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context, PermissionRequirement requirement)
    {
        var granted = await this.store.GetPermissionsAsync(this.user.UserId);
        if (granted.Contains(requirement.Permission))
        {
            context.Succeed(requirement);
        }
    }
}
備註：Handler 與快取
項目作用
PermissionStore依「使用者 → 角色 → 權限」取出此人所有權限的聯集（一人多角色時取聯集）
快取 5 分鐘每個請求都會授權，不快取會造成大量資料庫查詢
InvalidateAll()客戶在後台修改角色權限後呼叫，讓所有快取立即失效，變更即時生效
Enum.TryParse 過濾資料庫中若有已被移除的舊權限名稱，直接忽略而不報錯
PermissionHandler真正的判斷點：有此權限就 Succeed；沒有就什麼都不做，結果為拒絕（預設拒絕）
ICurrentUser使用者身分由前一頁「Session 與 JWT」的驗證流程建立，這裡只取用 UserId

步驟 5　註冊與預設政策

builder.Services.AddMemoryCache();
builder.Services.AddScoped<IPermissionStore, PermissionStore>();
builder.Services.AddSingleton<IAuthorizationPolicyProvider, PermissionPolicyProvider>();
builder.Services.AddScoped<IAuthorizationHandler, PermissionHandler>();

builder.Services.AddAuthorizationBuilder()
    .SetFallbackPolicy(new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());

app.UseAuthentication();
app.UseAuthorization();
備註：Program.cs 設定
項目作用
IAuthorizationPolicyProvider換成自訂提供者，才能動態產生權限 Policy
IAuthorizationHandler註冊 Handler，框架評估 Requirement 時會呼叫它
SetFallbackPolicy沒有任何授權屬性的端點，預設至少要登入。避免漏標變成公開 API
公開端點需要匿名存取的端點（登入、健康檢查）要明確標 [AllowAnonymous]
UseAuthentication → UseAuthorization順序不可對調：先還原身分，再判斷權限

步驟 6　啟動時同步權限並授予 ADMIN

public class PermissionSyncService : IHostedService
{
    private readonly IServiceScopeFactory scopes;

    public PermissionSyncService(IServiceScopeFactory scopes) => this.scopes = scopes;

    public async Task StartAsync(CancellationToken ct)
    {
        using var scope = this.scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var codes = Enum.GetNames<Permission>();
        var existing = await db.Permissions.Select(p => p.Code).ToListAsync(ct);
        foreach (var code in codes.Except(existing))
        {
            db.Permissions.Add(new PermissionEntity { Code = code });
        }

        var admin = await db.Roles.SingleAsync(r => r.IsSystem && r.Name == "ADMIN", ct);
        var granted = await db.RolePermissions.Where(rp => rp.RoleId == admin.Id)
                              .Select(rp => rp.PermissionCode).ToListAsync(ct);
        foreach (var code in codes.Except(granted))
        {
            db.RolePermissions.Add(new RolePermission { RoleId = admin.Id, PermissionCode = code });
        }

        await db.SaveChangesAsync(ct);
        PermissionStore.InvalidateAll();
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
備註：權限同步
項目作用
IHostedService應用程式啟動時自動執行一次，不需要人工維護權限表
同步權限清單把程式碼裡新增的權限寫進資料庫，後台的角色設定畫面就會自動出現新選項。程式碼是唯一來源（source of truth）
自動授予 ADMIN新權限自動給系統角色，所以不需要在 Handler 裡寫「若是 admin 一律放行」的特例
IsSystem標記系統內建角色，後台要禁止刪除或移除其權限，避免客戶把自己鎖在系統外
InvalidateAll()同步後讓舊快取失效

步驟 7　用測試防止漏標

[Fact]
public void Every_endpoint_declares_permission_or_allows_anonymous()
{
    using var factory = new WebApplicationFactory<Program>();
    var source = factory.Services.GetRequiredService<EndpointDataSource>();

    var missing = source.Endpoints.OfType<RouteEndpoint>()
        .Where(e => e.Metadata.GetMetadata<HasPermissionAttribute>() is null
                    && e.Metadata.GetMetadata<IAllowAnonymous>() is null)
        .Select(e => e.DisplayName)
        .ToList();

    Assert.Empty(missing);
}
備註：自動化測試
項目作用
EndpointDataSource取得應用程式註冊的所有端點，包含 Controller 與 Minimal API
檢查條件每個端點必須有 HasPermission 或明確 AllowAnonymous，兩者都沒有就是漏標
放進 CI新增 API 忘記標權限時，在合併前測試就會失敗，比上線後才發現安全

const requirePermission = (code) => async (req, res, next) => {
  const granted = await permissionStore.get(req.user.id);   // 快取的「使用者 → 權限集合」
  return granted.has(code) ? next() : res.sendStatus(403);
};

app.post('/orders/:id/approve', requirePermission('Orders.Approve'), approveHandler);
備註：路由檢查
項目作用
requirePermission路由層級的檢查函式，傳入該端點需要的權限代碼
permissionStore.get查使用者所有角色的權限聯集，需加快取並在後台修改時清除

Java／Spring Security

@PreAuthorize("hasAuthority('ORDERS_APPROVE')")
@PostMapping("/orders/{id}/approve")
public void approve(@PathVariable Long id) { ... }
備註：方法層授權
項目作用
@PreAuthorizeSpring Security 的方法層授權，需啟用 @EnableMethodSecurity
hasAuthority檢查登入者的 Authority；請在 UserDetailsService 載入時，把使用者所有角色的權限轉成 GrantedAuthority
用 Authority 而非 RolehasRole 預設加 ROLE_ 前綴，權限制請一律用 hasAuthority 以免混淆

Python（Django）

Django 內建 Permission 與 Group 模型，可在後台由管理者建立群組並指派權限。端點以 @permission_required('app.approve_order') 或 DRF 的 DjangoModelPermissions 檢查。客戶自訂角色對應到 Group 即可。

PHP（Laravel）

常用套件 spatie/laravel-permission：提供角色、權限模型與 permission:orders.approve middleware。權限在程式碼建立（seeder），角色由後台管理。
