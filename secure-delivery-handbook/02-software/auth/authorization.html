授權與存取控制

OWASP 排名居前的風險：驗證了身分，卻沒檢查「這個人能不能動這筆資料」。

原則

  • 預設拒絕，明確授權才放行；授權邏輯集中管理，不散落在各處。
  • 兩層檢查：功能層（角色可否呼叫此 API）＋資料層（此資源是否屬於呼叫者，防 IDOR／BOLA）。
  • 不依賴前端隱藏按鈕或不可預測的 ID 當作授權。
  • 模型選擇：RBAC（角色）為主；需要依屬性或情境判斷時用 ABAC／政策式。
  • 授權失敗與可疑存取要寫入日誌。

各技術實作

範例為最小示意，用來說明做法，套件 API 會隨版本調整，實作時請對照該版本的官方文件。上方篩選列可只顯示你用的技術。
[Authorize(Roles = "Admin")]
public IActionResult Delete(int id) { ... }

// 資源層：檢查此人能否編輯「這份」文件
var result = await _authz.AuthorizeAsync(User, doc, "CanEditDocument");
if (!result.Succeeded) return Forbid();
const requireRole = (role) => (req, res, next) =>
  req.user?.roles.includes(role) ? next() : res.sendStatus(403);

// 資源層：查詢時就帶上擁有者條件
const { rows } = await pool.query(
  'SELECT * FROM docs WHERE id = $1 AND owner_id = $2', [id, req.user.id]);
if (!rows.length) return res.sendStatus(404);
@PreAuthorize("hasRole('ADMIN')")
public void delete(Long id) { ... }

@PostAuthorize("returnObject.ownerId == authentication.name")
public Doc get(Long id) { ... }
# Django
@permission_required('docs.delete_doc', raise_exception=True)
def delete(request, pk): ...

# Django REST Framework：物件層
class IsOwner(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.owner_id == request.user.id
// Laravel Policy
public function update(User $user, Post $post): bool {
    return $user->id === $post->user_id;
}
// Controller
$this->authorize('update', $post);
